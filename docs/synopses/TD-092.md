# TD-092: the board's item file, its id and the reader for both versions

v3.0 makes the attention board a directory with one file per item, so two PRs that each add an item no longer
conflict (TD-070). That design ran nine rounds without settling, so you split it: this part designs only the first
two builds. B1 is the item file and its id. B2 is the reader that reads a v3 directory and a v2 board alike. The
writer, the merge gate's verdicts and the migration (B3 to B5) stay in TD-070's plan as a draft for a second part.

**The id (B1).** Every item gets a stable id, `YYYY-MM-DD-<8 hex>`: the day it was added and eight random hex
digits. The id never changes on a retitle, an edit or a close. An open item lives at `<id>.md` in the board's
directory. A closed one moves to `archive/<YYYY-MM>/<id>.md`, filed under the month it closed. `README.md` holds
what used to sit above the first item, and the old `docs/user_attention.md` becomes a short stub naming the
directory.

**The item file (B1).** An item file is written like a small ledger entry:
- a heading with the item's words;
- a block of header fields: `Kind`, `Added`, `Session`, `Context`, `Parts`, `Doer`, `Due`, `Hide until`, `Answers`,
  `Lifts`, `Decided` and `Closed`;
- the detail block;
- a `Log` of replies.

The module checks and writes these files, but it reads no file system and draws no random numbers. The caller passes
both in, as today.

**Reading (B2).** One reader, `load_board()`, gives one `Board` for both versions:
- **Form.** The `Board` carries its form (a directory or a file), the path it was read from, the major version its
  preamble declares, the open items, the closed items, and the problems found.
- **v2 boards.** A v2 board reads as it reads today, with the new fields filled from each line. A v2 item's id is
  its date plus a hash of its line's key.
- **Readers.** Every reader that took a v2 line now takes either form. The v2 string forms stay working until B5
  removes them.

**What a v2 board reads differently from B2 on.** The changes are small, and each one is written into *Versions*:
- An open line whose closed twin sits in the archive reads as closed.
- An id that appears only in a reply no longer counts as one of the item's references.
- A record's text is the item's words.
- The sweep reads its head phrase from the words only.
- An undated line has no id, and the sweep never closes it.
- A closed line is read as it is written.

A head's text beyond its session and host, such as `, branch x` in `(session a on h, branch x)`, is read into
nothing. The split will say so when it carries such a line.

**The rules are exact.** Each problem the reader reports has a numbered rule saying which board form raises it.
Each value has a stated type and a stated meaning when it is malformed. The prefix and date of a v2 line each have
one reading.

**The release order.** v2.8, the last v2.x minor, is cut before B1 merges, and B1 waits on your word that it is
cut. No release is cut between B1 and B5. B1 and B2 may build before B3 to B5 are designed: any change the second
part needs in them is a build of its own before v3.0.

**Alternatives weighed.**
- **A counter for the id, as the ledger's next id.** Every item written would need a take and a push, and items are
  written far more often than entries.
- **A hash of the item's words.** Two items with the same words would share one id. A hash gives only a migrated v2
  item its id.
- **Today's line as the file's first line, with its detail under it.** This keeps the old parsers, but also every
  cost of the line except the conflicts. The entry form is the larger build, chosen on long-term merit.
- **Leaving nothing at the old path.** An old reader would then see an empty board, which for a board says nothing
  needs you, and an old writer would start a second board there. So a stub stays at the old path.

**How the rounds went.** Six rounds ran, the cap for a format change. The design reviews raised 3, 3, 2, 1, 2 and
then 0 build-changing findings, so the rounds ended by the stop rule: round 6's review found nothing that would
make two builders differ. Every finding was applied, F175 to F257 (the record is `docs/reviews/TD-092.md`). The
closing fact-check found one slip in wording, now fixed. No design review has an unread build-changing fix.
