# TD-161: the merge check learns to recognise a question a tool asks you

ShiftLead's home tool can now ask you about one entry by landing a small change straight away, with no review. The
weekly audit cannot tell that change from any other unreviewed merge, so each one is reported as a problem and could
hide a real one. Nobody pressed anything to approve it, so its title proves nothing.

**The choice.** The merge check gets a new verdict that rebuilds the whole change from the state before it and passes
it only if the result matches byte for byte. A change that does anything more than hold one entry back and ask about
it goes to ordinary review.

**What passes.** One commit that changes one open entry and adds one board question. The entry gains the wait on you,
its question, context, answers and lifts, and a log of the asking. The board question must be exactly the one the regular
sweep would file for that wait.

**What goes to review.** Any other change to the entry, another entry or another board item; a dropped wait; an entry
already waiting on anyone's decision; answers the board could not offer; a person the board does not list; and dates
that do not fit the change.

**A stricter rule than the tool's own.** The tool misses two older ways of writing a decision that still hold an entry
back, and can add a second person beside one. The check refuses that. The shared writing step this design adds refuses
it too, so the tool gains the refusal when it adopts that step.

**The one choice you may want to weigh.** ShiftLead runs an older release, whose questions leave out a sentence newer
releases add when an open or decided board item already mentions the entry, such as a work order. The check does not make
an exception for this. Until ShiftLead takes the new release, those questions will often show in the audit as
unreviewed. The same holds for a question on an entry that already waits on someone, until ShiftLead adopts the shared
step. The alternative is to accept both forms, which would permanently let a tool leave
out a sentence you are meant to read.

**Options set aside.** Checking the change by a list of rules, which is wrong for entries with older status notes;
keeping the writing step private, which would leave ShiftLead with its own copy; and giving this kind of change a new
label in the existing commit reader, which could make older tools pass it unchecked; and giving the sweep the whole
ledger, which would not match what the tool computed.

**What it costs.** One build with its spec text, code and test cases together, then a minor release. agent-cadence
then takes the release and adds its review row. ShiftLead needs no change for the check to work, and a session would
hand it a follow-up to adopt the shared step.

**What happens next.** This waits on you. On Go, a session files the one build for the grinders and then hands
ShiftLead its follow-up. The release, which may share v3.6 with the three builds already waiting, is yours to cut.

**The rounds.** Four review rounds found 2, 1, 1 and 0 problems that would change the build. They covered reading the
question's words back exactly, how widely the older-release difference applies, and how the test data is kept. The
last round found only small points, and those are fixed. The closing check added two small refusals to the shared
writing step, which no reviewer has read, so the recommendation is one more round.
