# TD-148: a line that only separates two entries is no part of either

Many ledgers in the old single-file form put a horizontal line, written `---`, between one entry and the next. Every
tool here reads an entry from its heading to the next heading, so that line ends up as the last line of the entry
above it, inside whatever section came last. When that section is the question the entry asks the person, or its
list of answers, or its log, the tools go wrong in four ways: the check flags the question as running past its one
line, the question the person is shown ends in `---`, an entry's list of offered answers is refused, and a log that
ends the entry is flagged unreadable, so the question is treated as unanswered. Rewriting the entry cannot cure it,
because the rewrite would move the line under a new, empty-looking context section. When a ledger is split into one
file per entry, each file keeps its line, and from then on a note added to the entry goes below the line, which
buries it in the middle of the entry for good.

**The choice.** Such a line, when it is the very last thing in an entry with a blank line above it, is the entry's
*closing rule*: it belongs to no section, so every tool reads the entry as if it were not there, and every tool that
writes to the entry keeps it at the very end, below anything it adds. Nothing is deleted and no file is rewritten:
an entry with no such line reads and writes exactly as before, and every entry's saved form stays byte for byte the
same. It holds in the old single-file form and in the split files alike, since a split file keeps its line.

**How hidden notes are handled.** Entries may hold comments that are hidden when shown. Whether the last line is a
closing rule is decided with those comments set aside, which is how half the tools already read an entry, so all the
tools agree on it and the cut never runs through a comment. Comments next to the line go with it, and stay with it
at the end.

**What it does not do.** A line written directly under text, with no blank line above, is that text's underline as a
heading, so it is left as text and still flagged. A line anywhere else in the entry is ordinary text, as now. Split
files that an older tool already wrote a note below are not mended: there the line sits mid-entry and is flagged,
and deleting the line by hand fixes it. One rare shape is flagged where it was not before: a hidden comment holding
a code-block marker on each side of the line, which the person tidies by moving the comment.

**Options set aside.** Letting the line end the question anywhere in an entry, which would make it a new piece of
grammar; applying it to the old single-file form only, which would leave every split file wrong; having the split or
the formatter delete the line, which mends no ledger still in the old form and rewrites every split file to remove a
line that is already harmless; having the rewrite tool delete it, which breaks its promise to keep every word; and
having the check note every such line in a split file, which would put a note on every entry of every split ledger
for a line nothing reads.

**What it costs.** One build, the spec text, the code and the test cases together, then a small release. No other
repo changes its code: each takes the release as usual. Until it does, the flag stays a notice on its existing
entries, and blocks only an edit that makes a new one.

**The rounds.** Six review rounds, the most this kind of change gets, each one building the rule in a scratch copy
and running it on many invented entries. The point that kept coming back was hidden comments next to the line. It
was settled in round 3 by deciding the rule with comments set aside, and later rounds only tightened its edges and
the test descriptions. The last round found two problems that would change what the build writes, and the closing
check one: where the one blank line goes when a note is added to an entry that is only the line, a claim that the
writers' own read-back would catch a dropped line (it would not; the tests do), and a spec sentence still saying the
older rule. All three are fixed, but no reviewer has read the fixes yet. The recommendation is one more round, so a
reviewer reads them before the build starts.
