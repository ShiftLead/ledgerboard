# TD-152: a second question points at the first, and the merge check names the item it means

The tool that sweeps the ledger puts a question on your board when an entry is waiting on your decision and
nothing there asks it yet. It only recognises one shape of question: one that names the entry and the decision
exactly. If an older item already asks you about the entry in another shape, the sweep does not see it and adds
a second question beside it. Examples are a to-do step naming the entry among others, or a question naming
several entries or no decision. You answer whichever you see first. When that is the older one, your answer
cannot be used to release the entry. The check run before a change merges refuses the release, and its message
does not say which item it wants, so a session has to search for it. That happened on another repo's board on
2026-11-21: you closed an older to-do step, and the sweep's own question stayed open beside it.

**The choice.** The sweep still asks its question, but the question now says which older items also name the
entry, and that only an answer on this new one counts. It does not hold the question back while an older item is
open. An older item's answer cannot release the entry, so holding back would leave the entry with no question
that can release it. A to-do step that only mentions the entry in passing would then silence the question for as
long as it stayed open. The sweep also hands the list of older items to the program that runs it, which may show
a link from the new question to the old one.

**What counts as an older item.** An open item on any board the sweep reads that names the entry, or names the
entry's parent with the entry among its parts. Left out are plain notices, items about a different gate on the
entry, and the sweep's own items. An example of the sweep's own is the note it files when no board lists you,
which it closes itself once the question is asked.

**The merge check's messages.** The two messages that refuse a release now name the item that does ask the
question. When no item on the repo's board asks it, the one message that can then refuse says how the release
should be logged instead.

**What does not change.** Only an answer on the matching question releases an entry. Closing a to-do step never
releases one. An answer on a question naming several entries does not release any of them, because one question
for several entries already has its own form. When you did mean an answer elsewhere to count, the session you
drive records the release as an override, and review checks it. The tool that writes your answers accepts two
shapes the merge check does not count: a question with words after the decision, and one on a board that lists
nobody. That mismatch is left for a design of its own.

**Limits.** An older item opened after the sweep asks is not named, and the sweep never rewrites a question it
filed, so a named item that later closes stays named. Naming an item that only mentions the entry in passing is
accepted: the note is still true of it.

**Options set aside.** Holding the question back while an older item is open, or reporting only to the program
that runs the sweep; letting a question naming several entries release one of them; counting a closed to-do step
as an answer; warning when an item is written in the wrong shape, which would mean the board writer reading the
ledger every time.

**What it costs.** Two small builds, each with its spec text, code and test cases together: the merge check's
messages first, then the sweep's note. Then a minor release, which both builds may share. No consumer has to change its code. ShiftLead is
offered the chance to show the link.

**The rounds.** Six review rounds, this design's cap for a change to the shared formats, each followed by a
closing check from round 4 on. The early rounds found that the sweep's own items would be named, that the plan
claimed more about what releases an entry than is true, and that several test cases could not be written as
described. Round 3 found two problems in the wording of the spec text a builder copies. The design reviews of
rounds 4 and 5 found nothing that would change what is built; round 5's closing check moved the new spec
paragraph about the merge check's messages, which a fix had put inside an existing paragraph. Round 6 read that
correction and found it right. It found one problem that would change the build: three groups of test cases,
and a fourth it added, each hold several separate setups, and the plan said none needed a letter in its name, so
two builders could have stored them differently. Each setup now has its own lettered case, 24 in all. Its small
points were the plan's status line, a version note's wording, the merge check's advice now naming the exact
words to add to the release's log line, and a new case showing that a reminder to look or watch counts as an
older item. Its closing check found only two small wording points, both fixed. The rounds end here, at the
cap. No design reviewer has read the lettered cases, which change what a builder writes, so the recommendation
is one more round, a seventh, past the cap; Go is the alternative if you accept the fix as the review's own
suggestion.
