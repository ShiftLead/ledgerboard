# TD-124: the entry body grammar — strict section edges, one-line data

A ledger entry's body is split into **sections** (Why, Fix, Done when, Ask and so on), each opened by a bold label
at the start of a paragraph. Today the rule is loose: any paragraph that starts in bold opens a section, with or
without a colon. The tools read data out of some sections (the question an entry asks you, an event's check, and
soon an entry's own answers), so where a section ends decides what a tool reads. Three designs in a row had to
patch that edge, and the answers design spent four rounds on it before your hold. This design makes the edges
exact, so the data is exact, while the prose stays free.

**A section opens only at `**Name:**`.** A bold label ending in a colon, at the very start of a line that starts a
paragraph. A bold label with no colon (`**Done when** …`) or with the colon outside the bold stops opening a
section and becomes ordinary text. Every writer already writes the colon form. A fixed list of allowed section
names was considered and set aside: a repo's own sections (such as *Related*) would then need declaring, and the
colon already does the job.

**Mistakes are flagged, not read silently.** A `**Name:**` label stuck to the line above it opens no section, so
the ledger check flags it. A code block that is never closed is flagged too, since it hides everything after it.
Bold words anywhere else (inside a line, at the start of a bullet) are just emphasis and flagged by nothing.

**Data is one line.** A section a tool acts on is a single line, `**Name:** value`, and anything after that line in
the same section is flagged, never read. These are: the Ask (your question, one sentence), an entry's own Answers
and Lifts (TD-119), an archived entry's Resolved line, and a design's Design PR list. What an Ask carries today as
extra paragraphs of background moves to a separate **Context** section. Where data ever needs more structure than
one line, it goes in a single block of JSON (a structured text format), never in loose paragraphs; nothing needs
that today. An event's two-line check keeps its own exact form.

**Prose stays free.** Why, Fix, Done when, Context and any repo's own sections hold any text, bullets, code blocks
and bold words. The tools only find where each starts and ends.

**What the ledgers hold today.** Counted on this machine: about 50 open entries across agent-cadence and ShiftLead
write `**Done when**` with no colon, 19 archived ShiftLead entries have a label stuck to the line above, and only
this repo's two newest Asks have extra paragraphs. Nothing else would be flagged.

**The release, which is yours to choose.** The recommendation is two steps. First a minor release: the check flags
the four faults above, the writer refuses an edit that makes one, and a new command rewrites a whole ledger so
nothing is flagged, keeping every section's text and what the tools read the same (`**Done when** x` becomes
`**Done when:** x`, a stuck label gets its blank line, an Ask's extra paragraphs move to Context). Each repo runs
it in a pull request of its own: this one, then agent-cadence, then ShiftLead. Then a major release, v4.0, in which
the reader reads only the strict form, made once every ledger checks clean, so nothing reads differently on the
day. The other way is one major release that reads strictly at once: each repo would have to rewrite its ledger
in the same pull request that takes the new version, or about 44 of ShiftLead's open `Done when` sections would
silently join their Fix.

**What it does not touch.** The board's question files, which have their own form, and the entry's header lines
and history, which are already one item a line.

**Where it stands.** A first draft. The review rounds run after you choose the release; then the design comes
back to you for a go, and its builds are filed: the minor release, this repo's own rewrite, and the major release,
held until the other ledgers check clean.
