# TD-124: the entry body grammar — strict section edges, one-line data

A ledger entry's body is split into **sections** (Why, Fix, Done when, Ask and so on), each opened by a bold label
at the start of a paragraph. Today the rule is loose: any paragraph that starts in bold opens a section, with or
without a colon. The tools read data out of some sections (the question an entry asks you, an event's check, and
soon an entry's own answers), so where a section ends decides what a tool reads. Three designs in a row had to
patch that edge, and the answers design spent four rounds on it before your hold. This design makes the edges
exact, so the data is exact, while the prose stays free.

**A section opens only at `**Name:**`.** A bold label ending in a colon, at the very start of a line that starts a
paragraph. A bold label with no colon (`**Done when** …`) or with the colon outside the bold stops opening a
section after the major release, and stays flagged, so it never quietly joins the section above. Every writer already writes the colon form. A fixed list of allowed section
names was considered and set aside: a repo's own sections (such as *Related*) would then need declaring, and the
colon already does the job.

**Mistakes are flagged, not read silently.** A `**Name:**` label stuck to the line above it opens no section, so
the ledger check flags it. A code block that is never closed is flagged too, since it hides everything after it.
Bold words anywhere else (inside a line, at the start of a bullet) are just emphasis and flagged by nothing.

**Data is one line.** A section a tool reads a value from is a single line, `**Name:** value`, and anything after
that line in the same section is flagged, never read. Today that is the Ask (your question, one sentence), and,
once TD-119 is built, an entry's own Answers and Lifts. What an Ask carries today as extra paragraphs of
background moves to a separate **Context** section after it. An archived entry's Resolved line and a design's
Design PR list stay free text, since nothing here reads more than their first words. Structured data in a JSON
block is kept as a rule for later, when some field needs it. An event's two-line check keeps its own exact form.

**Prose stays free.** Why, Fix, Done when, Context and any repo's own sections hold any text, bullets, code blocks
and bold words. The tools only find where each starts and ends.

**What the ledgers hold today.** Counted on this machine: about 50 open entries across agent-cadence and ShiftLead
write `**Done when**` with no colon, 19 archived ShiftLead entries have a label stuck to the line above, and only
three of this repo's Asks (two open) have extra paragraphs. Nothing else would be flagged.

**The release: two steps, as you chose.** First a minor release. The check flags the four faults above, the
writer refuses an edit that makes a new one, and a new command (`migrate-body`) rewrites a whole ledger so nothing is
flagged: `**Done when** x` becomes `**Done when:** x`, a stuck label gets its blank line, and an Ask's extra
paragraphs move to Context. It changes what a tool reads only where that is the point: a stuck label becomes the
section its writer meant, and a long Ask is read as its first paragraph. It refuses, for a person to fix, what it
cannot rewrite safely: an unclosed code block, an indented Ask, a label that would turn into a name the tools read
(`**Done when.**`), an Ask whose wording it would have to squeeze. Each repo runs it in a pull request of its own:
this one, then agent-cadence, then ShiftLead. Then the major release, v4.0, reads only the strict form, once every
ledger is rewritten and the command would change and refuse nothing, so nothing reads differently that day.

**While a repo waits to rewrite.** The check counts each kind of fault per entry, so an edit to an entry that
already has old-style labels passes, and only a new fault fails. Closing an unclosed code block by hand is never
refused, even though it uncovers faults that were hidden.

An Ask written indented or as a quote is flagged too, since the tools would not see it. **Context** becomes a
reserved name: a repo's own section called Context is read as its Ask's background.

**Comments.** HTML comments (hidden notes in the Markdown) are read the way the writing tools read them: a line
holding only a comment counts as text, so a label right after it is stuck; a label inside a comment is left alone.

**What it does not touch.** The board's question files, which have their own form, and the entry's header lines
and history, which are already one item a line. Some looks-alike stay plain text: a bold label inside a line or as
a list item, and a paragraph cannot start with bold emphasis without being a section or flagged.

**Builds.** The minor release (with a way to write the Context after the Ask); this repo's own rewrite; the major
release, waiting on each other repo's rewrite pull request; and a later change so the sweep's question carries the
Ask's Context. On your go a session asks agent-cadence and ShiftLead to file their own: taking the release, making
their Ask writers write one line plus Context, and running the rewrite.

**The rounds.** Six, the most allowed. Problems that would change the build, per design review: 7, 4, 5, 3, 3, 2,
each round narrower, all in two places: telling a new fault from an old one, and making the rewrite exact around
comments. The last review judged the design worth building as it stands. Its six fixes, two of them build-changing (where the Context goes when a comment holds a blank line, and leaving
faultless entries alone), are read by no design reviewer, so the
recommendation is one more round.
