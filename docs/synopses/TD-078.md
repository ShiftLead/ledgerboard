# TD-078: v3.0's ledger half — the last migration, a note for archived entries, and the removals

v2 still reads four old forms, only because old files hold them: a `Waits` field, a `Taken by` field, the old
decision form `decision (<who>) <text>` in `Blocked by`, and a `Resolved` header field. v3.0 stops reading them and
removes `migrate`. Before that can happen, every repo that takes v3.0 must hold none of them, open or archived, with
no hand edit. The design gives v2.8 the last `migrate` and a note for archived entries, and v3.0 the removals.
Since your input of 2026-11-13 (TD-096), it also says how the roster repos get there: one remodel each, straight to
v3.0, after it is cut.

**The last migration (B2, in v2.8).** `migrate` gains four rules:
- `Taken by` becomes one plain Log line, `Taken by <value>`.
- `Waits` becomes one Log line on an archived entry. On an open entry it stops the run, since the wait needs a real
  gate (`until` or `event`) that someone chooses and `set` writes.
- A header `Resolved` moves to the body's `**Resolved:**` section. Where the body already has one, the run stops.
- The old decision form becomes `decision (<who>)`. Its text goes into an `**Ask:**` when the entry has none. When
  it has one, the existing Ask stands and the old item goes whole into one Log line. The run stops when `<who>` is
  neither a person nor a retired role, when an open entry has no Ask and the old item has no text to give it, and
  when the same `decision (<who>)` is already there.

The new Log lines are dated so that no gate's age moves. Under v2.8 the merge gate counts an old-form holder in the
base as a decision already there, so the rewrite does not read as gaining decisions. Once a repo has migrated, the
gate sweep sees decisions the old form hid, and may owe each a board item, which is right.

**A note for an archived entry (B1, in v2.8).** `ledger.py note TD-n "…"` takes an archived entry and writes it
where it is. It refuses one whose Status is outside the closed set. `set` and `edit` still take only open entries.

**The release order.** B1 and B2 have merged (TD-088, TD-089), and this repo's own ledger has been migrated with
them (B3, TD-090). v2.8 is tagged (2026-11-13, #281) and holds them. It is the last v2.x minor, unless a v2.9 is cut
before TD-070's first build merges. Then come TD-070's builds, then the removals (B4, TD-091), then v3.0, which is
yours.

**What v3.0 removes (B4).** Each of the four forms, and a header `Location`, becomes a `retired` error on every
entry of a v2 ledger, open or archived, whether or not the edit touched it. On a v1 ledger a retired field is only
ℹ. The old decision form is also an unreadable item, so it is an error on an open entry even there, and ℹ on an
archived one. One helper with its own pattern finds the old form. `migrate` goes, with everything only it used.
v3.0's merge gate no longer counts an old-form holder in the base. So an old form rewritten as `decision (<who>)`
reads as a new decision, which needs a board item. The ledger's declared major stays 2.

**The precondition.** It binds the three repos that take v3.0 when it is cut: ledgerboard, agent-cadence and
ShiftLead. A repo is ready when, run with v2.8, `migrate --plan` shows no entry with changes or stops. Each consumer
runs it in its v3.0 vendor PR. Ledgerboard runs it before B4, with v2.8's own module. SPEC says the same without
naming repos: a ledger whose repo stays on an older release is untouched by v3.0 until that repo takes it. Before
then, it runs the last v2.x `migrate`, with a tool that still carries it.

**A roster repo's one remodel (D7).** The roster repos are the repos other than these three that pin
agent-cadence. They skip their v2.7 remodel. When its own team picks a repo up again after v3.0, that repo takes one
remodel: one session and one PR, with two bumps of its agent-cadence pin.
- **The pins.** agent-cadence writes a remodel procedure, at a fixed path on its `main`, that names both pins. The
  first is a commit that vendors v2.8. The second is one that vendors v3.0 or later. The procedure lands in two
  PRs:
  - The first PR holds the procedure, its first pin, and a test of its commands at that pin. It merges before
    agent-cadence's v3.0 vendor PR, which waits for that test to pass. A defect at the first pin is then found
    while agent-cadence's `main` still vendors v2.8, and is fixed there by naming a newer first pin.
  - The second PR names the second pin and tests there, after the v3.0 vendor PR.

  A later PR whose test passes may name newer pins. If a first-pin defect turns up only after v3.0 is vendored, it
  is fixed on a maintenance branch of agent-cadence cut from the first pin. That branch's fixed commit becomes the
  first pin, and the branch is kept. agent-cadence's `bump` must then accept a pin off `main`, and the second bump
  from it to a v3.0 commit that does not descend from it. Today `bump` refuses both. `migrate` stays usable under
  the first pin after v3.0 removes it, because that commit stays. No roster remodel starts before the procedure
  names both pins.
- **What the PR shows between the bumps**, under the first pin, for the techlead who merges it:
  - the ledger is a v2 directory (a one-file ledger is split first);
  - `migrate --plan` shows nothing;
  - every entry is canonical (`ledger.py fmt --check` exits 0);
  - no open entry holds the retired `hold` or the reserved `decision (designer)`;
  - `ledger.py --check` shows no error;
  - the board carries its `People:` line and is in `fmt`'s form.

  The merge gate never sees this middle state. It reads only the PR's start and end.
- **How v3.0 grades it.** At the PR's head, under the second pin. Any old form left is a retired error. Every
  decision the remodel wrote reads as new, so each needs a covering board item. It is written after the board's
  split, in the form TD-095 designs.
- **The board.** It gets the v2.x steps it missed under the first pin, and its split under the second. TD-095
  designs the split, including a board that predates v2.3.

The commands, their order and their commit points are agent-cadence's procedure, not this design's. In rounds 11
and 12 every command-level finding was about an agent-cadence wrapper, which this repo cannot check and which
changes without a ledgerboard release. The procedure's requirements, as the rounds found them, are listed under
agent-cadence's *Consumers* line. They include the order of the split and `migrate` (archived dates), how a
missing date is answered, fixing what `canonical()` refuses before any writer runs, `fmt` after `migrate`, and the
board writer's flags and commits. Target design §7.2 moves the roster remodels and their *quiet first* order
(fewest stops first) to a new step 7, after v3.0.

**Choices weighed for the roster.** Two PRs per roster repo, the first merged under the v2.8 pin, so v2.8's gate
grades the rewrite and its decisions need no board item there: two remodels where you asked one, and the board
items are owed anyway. Keeping `migrate` in v3.0 for the roster: the old forms' code would stay in every v3.x reader
for a run each roster repo makes once, under a pin that already has it. v3.0 keeping the base-side count for a
roster rewrite: a v3.0 reader carrying a retired form's meaning. A remodel reads the pins once, when it starts, so a
defect found partway is met by restarting on a newer pin.

**What the consumers do.** These are lines for their own entries, filed through each repo's question seat.
- **agent-cadence:** before its ledger migrates, an id that is a real wait moves out of the old form's text into
  `Blocked by`. Its v3.0 vendor PR removes its `migrate` command and its date helpers, the `accept_taken_by` keyword
  and the `old_form` read. Its tests read a roster-shaped fixture without error, since its tools still read
  un-remodelled roster repos. It writes the remodel procedure above in its two PRs, the first before its v3.0 vendor
  PR. Its `run` and `bump` accept a maintenance-branch pin and the second bump from it.
- **ShiftLead:** its Queue card's *held until …* reads the `**Ask:**` before its ledger migrates. It vendors the
  minor and runs `migrate` in separate PRs.

**Left out.** The board's half of v3.0 (TD-070, TD-095). When v3.0 is cut. Renaming `**Resolved:**`. Removing the
Status note lift.

**The revision's rounds (TD-096).** Six rounds, 9 to 14, ran to the cap. You bought a fifteenth (TD-097).
Build-changing findings per design review: 1, 2, 5, 1, 2, 2, then 1 in round 15. Fact-checks, with their re-checks:
2, 0, 1, 0, 0, 0, then 0. Round 15's closing fact-check raised one build-changing finding. Four topics came back
across rounds:
- **The first pin.** It went from the last commit before a merge, to a tag, to a vendoring PR's commit, to the
  newest passing one, to the procedure's file, which can name a newer pin. In round 15 it came back twice. The
  design review found that a newer first pin cannot exist once v3.0 is vendored, so the procedure now lands in two
  PRs, with the first pin tested before v3.0, plus a maintenance branch as the last resort. The closing fact-check
  then found that agent-cadence's `bump` refuses the second bump from such a branch, so that is now a requirement
  on agent-cadence.
- **The remodel's commands.** They ended when round 11 moved them to agent-cadence.
- **How v3.0 reads the old form on a v1 ledger.** It did not come back in round 15.
- **The old-form detector.** It did not come back in round 15: the design review checked the helper's pattern
  against B4's fixtures.

Round 15's design review judged the first pin "fixable, not the design wrong". Each round's fix has made the first
pin's path safer, and each time the next round found a seam in that fix. The closing fact-check's fix (F222) has been
read by no design review. It is a requirement on agent-cadence's `bump`, which a later agent-cadence entry builds.

The recommendation is **One more round**: a design-changing fix is unread, and the first pin has now recurred in
four rounds (9, 13, 14 and 15). Is this the wrong design? The alternative to two pins would be one of the choices
already weighed above, each rejected for a reason that still holds. Go is the alternative if you judge that a
requirement on agent-cadence's `bump`, tested there, needs no further review here. On Go, B4 (TD-091) gains text
5′, the new clauses in texts 7 and 12, the helper and the new fixtures, and its block on TD-096 drops.
