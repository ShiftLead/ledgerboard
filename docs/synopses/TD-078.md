# TD-078: v3.0's ledger half — the last migration, a note for archived entries, and the removals

v2 still reads four old forms, only because old files hold them: a `Waits` field, a `Taken by` field, the old
decision form `decision (<who>) <text>` in `Blocked by`, and a `Resolved` header field. v3.0 is planned to stop
reading them and to remove `migrate`, once no repo holds any of them, open or archived. Two things stand in the
way. No writer rewrites them: `migrate` leaves all four as they are, and no writer can touch an archived entry,
which leaves a hand edit across some 200 old forms in three repos. And an archived entry cannot even take a note,
which PR #226 ran into on 2026-11-11.

**The last migration (B2).** `migrate` gains four rules, in the last v2.x minor:
- `Taken by` becomes one plain Log line, `Taken by <value>`.
- `Waits` becomes one Log line on an archived entry. On an open entry it stops the run, since the wait needs a real
  gate (`until` or `event`) that someone chooses. No open entry has one today.
- A header `Resolved` moves to the body's `**Resolved:**` section. Where the body already has one, the run stops.
- The old decision form becomes `decision (<who>)`. Its text goes into an `**Ask:**` when the entry has none. When
  it has one, the existing Ask stands and the old item goes whole into one Log line.
- The old form also stops the run when `<who>` is not a person, when an open entry has no Ask and the old item has
  no text to give it, and when the same `decision (<who>)` is already there.

The new Log lines are dated by the entry's filing date. On an open entry carrying a gate they are dated so that
none can become the Log's first dated line, so no gate's age moves. The merge gate counts an old-form holder in
the base as a decision already there, so the migrate PR does not read as gaining new decisions. A migrated entry
that still holds a form, or gains an `ask-missing` or `gate-repeated` error, stops the run.

**A note for an archived entry (B1).** `ledger.py note TD-n "…"` takes an archived entry and writes it where it is
in `archive/`, with no flag. It refuses an archived entry whose Status is outside the closed set, so one test says
when an archived entry takes a note. `set` and `edit` still take only open entries: changing what an archived
entry says is a `reopen`, an edit, then an `archive`. A stale line in an archived Log is corrected by a later dated
line, never rewritten.

**The release order.** B1 and B2 ship in the last v2.x minor (v2.8, or v2.9 if v2.8 is cut first). TD-070's
design allows no v2.x release after its first build, so TD-070's B1 waits on TD-078's B1 and B2 and on your answer
that the minor is cut. Then this repo runs the new `migrate` on its own ledger (B3): on 2026-11-12 that changes four
entries, this one among them. Then TD-070's builds, then the removals (B4), then v3.0, which is yours.

**What v3.0 removes (B4).** Each of the four forms, and a header `Location`, becomes a `retired` error on every
entry, open or archived, whether or not the edit touched it, so `--check` and the merge gate fail on it. An
old-form item reads as an unreadable item, and every code path that handled it goes. `migrate` goes, with
everything only it used. The closed Status set's message, which said *run migrate*, says how to fix the Status by
hand instead. Lifting a Status's notes into the Log stays, but no longer reads a header `Resolved` for its date.
The ledger's declared major stays 2.

**The precondition.** A repo is ready for v3.0 when, run with the last v2.x minor, `migrate --plan` shows no entry
with changes or stops. Each consumer runs it first in its v3.0 vendor PR and records the output. No new check is
added.

**What the consumers do.** These are lines for their own entries, filed through each repo's question seat.
- **agent-cadence:** its `prose_waits` reads ids out of the old form's text, so before its ledger migrates, an id
  that is a real wait moves into `Blocked by` (TD-144's `shiftlead#TD-1029`). `note` on an archived entry needs no
  change in its wrapper. Its own `migrate` command runs the minor's rules. Its v3.0 vendor PR removes that command
  and its two date helpers, the `accept_taken_by` keyword and the `old_form` read.
- **ShiftLead:** its Queue card's *held until …* reads the old form's text, so it must read the `**Ask:**` before
  its ledger migrates. It vendors the minor and runs `migrate` in separate PRs, so the newer merge gate grades
  the rewrite. That run stops today on five archived Statuses, each answered in its PR.

**Left out.** The board's half of v3.0 (TD-070). When v3.0 is cut. Renaming `**Resolved:**`. Removing the Status
note lift.

F86). Round 5 found that they described the older agent-cadence tree this repo pins rather than agent-cadence's
