# TD-150: a person's question waits until the work it depends on is done

The tool that sweeps the ledger for stuck entries asks you a question whenever an entry is waiting on your decision
and nothing on the board asks it yet. It does this even when the entry is also waiting on other work that is still
going on. The case that matters: when you answer "one more round" on a design, the bought review round becomes an
entry of its own, and the design waits on both that round and your decision. Thirty days after your answer, the
sweep asks the design's go-ahead again while the round may still be running, a question you cannot answer yet. A
"Go" there would not let the design itself be built, since it still waits on the round. But the design's waiting
builds are each asked their own go-ahead at the same time, and a "Go" on one of those lets that build start before
the round's reviewers have read the fixes you bought the round for.

**The choice.** While an entry is blocked by another entry that is still open, the sweep does not ask your
question about it. Once that work ends, the question is asked as before. The same holds for a design's builds that
wait with it: while the design is held by an open round, their own go-ahead questions are not asked either. The
check run before a change is merged holds the same way: it no longer insists that such a question be put on the
board straight away, and notes instead that it is waiting. Because that check cannot look at other repos, an entry
blocked by any other repo's entry, even a finished one, gets the note instead of the refusal; the sweep then asks
the question once it sees the work has ended, so the question is delayed, never lost.

**What counts as work still going on.** An entry still in the ledger, or one replaced by another that is still
open. Work that has ended, been dropped, or cannot be found does not hold the question back, so a mistyped
reference never silences it. A design's own builds never hold back its go-ahead, or it would never be asked.
Waiting on a date, an outside event or another person's decision does not hold it back either.

**Another repo's entry.** The sweep can only tell whether another repo's entry is open if the program running it
supplies a way to look. Where it cannot tell, it asks as it does today, rather than going silent for good. Asking
then costs little: the other repo's entry still blocks the work after a go-ahead.

**What it does not do.** A question already on the board stays there. Very old archive entries whose status still
uses retired words are read by the sweep as open, so a question waiting on one is not asked until that status is
corrected, which the existing checks already ask for.

**Options set aside.** Closing a question already asked when new work is added; holding a question back until
nothing else at all blocks the entry; adding a new list of held-back questions to the sweep's result; restarting
the thirty-day wait when the blocking work ends.

**What it costs.** One build, with the spec text, the code and the test cases together, then a small release. The
two programs that run the sweep each pass in their way of looking up another repo's entries when they next take the
release, and show the new note.

**The rounds.** Five review rounds and a closing check. Early rounds found that a design's waiting builds would
still be asked, and tightened how the test cases are laid out. The last round and the closing check found nothing
that would change what is built. The recommendation is Go.
