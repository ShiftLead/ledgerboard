# TD-111: a shared check for text a person reads

Paul switches between projects, so what a session leaves for him has to read cold: a question on the board, its
answers, a ledger entry's question, an entry's title. ShiftLead wrote down the rules on 2026-11-14 and asked for
one check that both agent-cadence and ShiftLead run, so the two do not each keep a copy that drifts. This design
puts that check in ledgerboard, the format library both of them already copy in.

**The rules.** A question or a task is one plain sentence of at most 25 words. It has no code in it: no file
name, path, function name, command option and so on. A question ends in a question mark. Every answer says who
acts: *I*, *you*, or someone else the writer's process knows, such as *a session*. A title is plain words, with no
code and no internal label such as a ledger id. The longer context may be any length. Code in the context gets a
warning, never a refusal.

**What stays out of ledgerboard.** ledgerboard may not know either tool that uses it. So the check's grammar is
shared, and its vocabulary is handed in by whoever runs it. The grammar covers what code looks like, what one
sentence is, and plain English words such as *I*, *you*, *we* and *nobody*. The vocabulary covers the roles that
act in a process (*session*, *seat*, *techlead* and the rest), its sessions' coined words (*slice*, *seam*), and
its label shapes (*B4*, *F12*, a pull request's *#123*). ledgerboard keeps only its own ledger ids (*TD-12*) as
labels.

Three other options were weighed and rejected. Keeping ShiftLead's words inside ledgerboard would refuse right
answers in any other process. Declaring the words in each repo's files would copy one process's words into every
repo, where they would drift. Leaving the whole check to each tool is the drift TD-111 exists to end. The two tools still need one shared word list between them, or their lists can
drift. That is theirs to settle: the design asks them to, and does not choose for them.

**Who runs it.** The tools' own writers run it when a session writes a question, answers or a title. A refusal
lists every problem, so the session can fix them all in one rewrite. A board task (an *act* item) must open with
its task in bold or it is refused; a board question with no bold opening is read whole. ledgerboard's own internal writing functions never
run it, because sweeps and migrations write through them and must not be stopped by words no session just wrote.
ledgerboard's own command lines do not run it either. They hold no word list, so they would wrongly refuse *a
session pins it*. The alternative, giving them flags for the word lists, was weighed and rejected for that reason. ledgerboard's techlead agreed with this on 2026-11-14. The format text says exactly which
writes a writer checks, and what counts as the question, the answers and the context for each. For a ledger
entry's question, the first paragraph is the question and the rest is context, so a session puts a blank line
after the question. A board question with no bold lead is read whole, so a second sentence belongs in its
details. A person's name in an answer
counts as who acts, whatever its capitals; so on a board whose people include someone named Will, *it will be
built* passes. A retitled entry's new title is checked too.

**What changes for questions written today.** Most ledger questions written today are instructions, such as *Say
Go to file the one build, One more round, or Hold with a note*. Under this check a question must be one sentence
that ends in a question mark. The tools' templates for these questions change with it, and the design tells both
tools so.

**Known mistakes the check makes.** Some plain words look like code and are refused: *yes/no/maybe* and
*he/she/they* look like paths, *Node.js* like a file name, *iPhone* and *macOS* like code names. A label pattern a
tool hands in may also catch a plain word, such as *P0* or *S3*. An abbreviation the check does not know, such as
*Ph.D.*, reads as the end of a sentence; the common ones (*Dr.*, *p.m.*, *Nov.*) are known. Each problem line says
how to fix the text, and each mistake found later is added to the format's test cases. The check also misses
some things. A link's address and a bare web address are skipped. *Say no. Then what?* reads as one sentence,
because *no.* is read as an abbreviation (*No. 5*). *the US market* counts as naming who acts, because *US* reads
as *us*. A ledger id such as *TD-109* is allowed in a question, since ShiftLead's rules do not count an id as code, and
is refused only in a title.

**What changes from ShiftLead's version.** Besides the handed-in word lists, the design settles what ShiftLead's
text left open. It pins the exact wording of every problem line; one of ShiftLead's examples disagreed with its
own rule, and the rule wins. It pins how code is found when a link sits inside it, and that a dash or a slash
alone is not a word. It adds contractions such as *we'll* that ShiftLead's list missed. ShiftLead's design text
and one step of its follow-up entry name word lists this design does not provide; amending those is ShiftLead's
job.

**The release.** It ships as a minor release: new functions, and nothing existing changes. Paul cuts the
release, as for every ledgerboard release. The build does not wait for TD-109's build. When the build merges, agent-cadence's techlead is told which release carries it. agent-cadence copies it in first, then
ShiftLead.

**Not done.** No old board or ledger is swept for these rules. ShiftLead's rules about passed-up questions and
its **Not clear** button stay ShiftLead's.
