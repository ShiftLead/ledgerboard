# TD-109: an Ask with no decision gate is flagged

An entry can wait on a person and nothing shows it. When an entry has an `**Ask:**` section (the question a person
owes an answer to) but no `decision (<person>)` gate in its `Blocked by`, it reads as ready to pick up, no board item
is made for it, and the person never hears that something waits on them. agent-cadence met this on 2026-11-14 and
built a check into its own wrapper; this design moves the check into ledgerboard, so every consumer's writer has it.

**The flag.** `check()` flags an open entry with an Ask and no decision gate: `decision-missing`. It is an error on
an entry an edit changed, so the ledger writer refuses a write that makes one, and a note (ℹ) on an entry nobody
touched. A retired gate (`hold`, `decision (designer)`) or the old decision form counts as a decision here, since
each already has its own error. A date or event gate does not: they name no person.

**An answered question is not flagged.** When a decision is lifted (the person answered, on the board or by hand
through the writer), the Ask stays in the entry as the record of what was asked. The check reads the entry's Log:
if the last decision line there is a `gate lifted`, the Ask was answered and nothing is flagged. Because the Log is
kept for good, this reads the same on every later edit, not only in the PR that lifted the gate.

**Writing a wait.** Today a session writes the Ask first, then the gate, as two writes. With the flag that no
longer works in either order: an Ask with no gate is now refused, and a gate with no Ask already was. So:
- `ledger.py set TD-n --blocked-by "…, decision (<person>)" --ask FILE` writes the gate and the Ask in one write;
  `new` takes `--ask` too.
- Writing an Ask onto an entry with no decision gate is refused, by the module itself, so an answered Ask is never
  quietly turned into a new, ungated question.
- `edit TD-n --section Ask --remove` removes an Ask from an entry that waits on no one.
- An entry whose question was answered can be gated again without restating it; the session rewrites the Ask if the
  question changed. A guard against that was designed and then dropped as more trouble than it saves.

**What it leaves alone.** An `Owner` that names the person, with no gate, is not flagged. Owner is a ledger's own
field, so ledgerboard cannot tell which values name a person, and the consumers use it differently: agent-cadence
treats it as a wait, ShiftLead uses it on purpose for work only the person can do with a session. agent-cadence
agreed (2026-11-14) to keep its own Owner check and drop its Ask check once it takes this release. Nothing changes
whether an entry is pickable.

**Release.** A minor (v3.1 unless another lands first): no field, Log line or key is new, and every file v3.0 wrote
reads the same. Two things change for consumers when they take it, and the design files an entry in agent-cadence
and in ShiftLead for each: their "Ask, then gate" steps become one `set --ask`, and a direct `edit_entry()` call
that writes an Ask on an ungated entry is refused. Existing entries with an unanswered, ungated Ask show as notes;
each consumer cures them (add the gate, or remove the Ask) in a PR right after taking the release, since any later
PR that touches one fails its check. One build, B1, carries the SPEC text, the code and the fixtures.

**The rounds.** Six rounds, to the cap; the last design review found nothing that changes the build. One topic kept
coming back: how an Ask and its gate get written together (the one-write `--ask`, its edge cases, and a re-ask
guard that was added and then withdrawn). The last reviewer judged that mechanism heavy but right: the simpler
alternative, renaming an answered Ask's heading when its gate lifts, would change the lift format and flag every
entry already answered.
