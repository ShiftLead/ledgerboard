# TD-115: a merge-gate verdict for a PR that only lifts a gate

ShiftLead's **Lift the hold** button, as its design writes it, lifts a person's hold on a ledger entry itself: one
PR that removes the entry's `decision (<person>)` gate and logs who lifted it and with which answer. The merge gate
has no rule for that shape. Its one carve-out for a person's answer takes only a PR that answers an open question
on the board, so this PR goes to ordinary review, and agent-cadence's audit counts it as merged outside the rules.
This design adds a second carve-out, so the button's PR can merge on its own, as an answer on the board already can.

**What it trusts.** A carve-out skips review, and the lift's only trace, its Log line, can be forged. So the
verdict trusts exactly what the existing carve-out trusts: that every byte the PR changes is what the package's own
writers produce from the PR's base, for one answer by the gate's own person, listed on the board's `People:`. It
works out the right form of the lift from the base board itself and compares bytes, so a PR cannot choose its own
form or change anything else. Anyone answering for someone else, even where the board allows it, goes to review.

**The four board states.** What the lift must look like depends on what the board holds about the gate:
- **An open question asks it:** the PR goes to review. That question's own answer is the way to lift it.
- **An answered item still stands open** (a work order the person gave): the lift closes it, `— lifted`, in the
  same PR, and only if the person's own name is on that answer.
- **A shared question asks it and other entries:** the lift takes this entry out and leaves the question open for
  the rest.
- **Nothing asks it:** the lift says so, and the board is untouched.

**Where it reaches further than an answer on the board.** These are accepted, since the button is meant to lift
(Paul, 2026-11-14: *lifts are allowed by a button press*): a gate with no question on the board lifts in one PR,
not two; a shared question loses one of its entries without being answered; and the person's open work order is
closed by the lift. The worst a forged PR can do is lift one gate, and close that person's work orders on it.
Nothing in the format re-reads the lift after it merges. The backstop is the consumer's own audit: agent-cadence
lists such merges apart in its weekly read.

**Where it is stricter than the button.** Three presses the button makes still go to review: closing an item
answered by someone else or by no one, a press on a board with no `People:`, and any press on an old-format (v2)
board. ShiftLead's own board is still the old format, so ShiftLead's own lifts keep taking review until it moves.

**What else ships.** The PR's commit subject becomes part of the format (`<tool>: lift decision (<p>) on TD-n
(session <s>)`, ShiftLead's own subject word for word) with a writer and a reader. A helper names the lift's form
for a given board, so the button and the verdict cannot disagree. Something that cannot be read is reported as a
reason, except the existing tripwire's own refusal, which surfaces exactly as it does for today's verdict.

**Release.** A minor release, v3.2: nothing already written reads differently, except that the subject's kind now
reads `lift` where it read nothing. v3.1 is on main but not yet tagged, and a release stamps whatever main holds,
so the one build waits for v3.1's tag. Then agent-cadence wires the verdict into its merge check, and its techlead
is told which release carries it. ShiftLead needs no change to its subject.

**Options set aside.** No carve-out at all (every press waits on a reader for a two-line diff the verdict can check
whole); trusting the tripwire alone (the PR would choose its own form and could change other files); allowing only
the answered-item state (most presses would go to review); folding it into today's verdict (that changes the
reasons it gives its callers); refusing an entry the person owns, as the button does (that is ShiftLead's
policy, not the format's).

**The rounds.** Six rounds, to the cap; the last design review still found one build-changing point, about the
release number. Three topics kept coming back: how far the trust argument reaches (each pass made it more honest,
and the last two reviewers judged it sound), the release number (each fix met a release state the last one
missed), and what to do with text that cannot be read (settled by doing what today's verdict does). The last
fixes were fact-checked but not design-reviewed, so the recommendation is one more round.
