# TD-115: a merge-gate verdict for a PR that only lifts a gate

A **gate** is a hold on a ledger entry: `decision (<person>)` means nobody builds the entry until that person says
go. ShiftLead's **Lift the hold** button, as its design writes it, removes such a hold itself: one pull request
that takes the gate off the entry and adds a line to the entry's history (its Log) saying who lifted it and with
which answer. The merge gate, the check that decides whether a pull request may merge without a reviewer, has
no rule for that shape. Its one exception for a person's answer (a **carve-out**: a kind of pull request it lets
through unreviewed) takes only a pull request that answers an open question on the board, so this one goes to
ordinary review, and agent-cadence's audit counts it as merged outside the rules. This design adds a second
carve-out, so the button's pull request can merge on its own, as an answer on the board already can.

**What it trusts.** A carve-out skips review, and the lift's only trace, its history line, can be forged. So the
new rule trusts exactly what the existing carve-out trusts: that every character the pull request changes is
what the package's own writing tools would produce from the starting point, for one answer by the gate's own
person, who must be listed on the board's list of people. It works out the right form of the lift from the
board itself and compares the text exactly, so a pull request cannot choose its own form or change anything else.
Anyone answering for someone else, even where the board allows it, goes to review.

**The four board states.** What the lift must look like depends on what the board holds about the gate:
- **An open question asks it:** the pull request goes to review. That question's own answer is the way to lift it.
- **An answered item still stands open** (a work order the person gave): the lift closes it, marked as lifted, in
  the same pull request, and only if the person's own name is on that answer.
- **A shared question asks it and other entries:** the lift takes this entry out and leaves the question open for
  the rest.
- **Nothing asks it:** the lift says so, and the board is untouched.

**Where it reaches further than an answer on the board.** These are accepted, since the button is meant to lift
(Paul, 2026-11-14: *lifts are allowed by a button press*): a gate with no question on the board lifts in one pull
request, not two; a shared question loses one of its entries without being answered; the person's open work order
is closed by the lift; and a gate asked only on another repo's board counts here as "no question", so the lift
passes and leaves that other repo's question open. The worst a forged pull request can do is lift one gate, and
close that person's work orders on it. Nothing in the format re-reads the lift after it merges: the backstop is
the consumer's own audit, as agent-cadence lists such merges apart in its weekly read.

**Where it is stricter than the button.** Three presses the button makes still go to review: closing an item
answered by someone else or by no one, a press on a board with no list of people, and any press on a board still
in the old single-file format. ShiftLead's own board is still in the old format, so ShiftLead's own lifts keep
taking review until it moves.

**What else ships.** The pull request's commit title becomes part of the format (ShiftLead's own wording, word
for word), with a tool that writes it and one that reads it. A helper names the lift's form for a given board, so
the button and the merge rule cannot disagree. Text that cannot be read is reported as a reason to send the pull
request to review, except where the existing safety check refuses it first, which surfaces exactly as it does today.

**Release.** A minor release, v3.3, which Paul cuts: nothing already written reads differently, except that the
commit title's kind now reads "lift" where it read nothing. v3.2 is already released, so the build needs no
release first, but it is filed only after TD-119's matching wording has merged: the design that lets an entry
offer its own answers (TD-119) also goes into v3.3, and each writes its own release note, as the format's list of
releases already holds several notes for one release. If v3.3 is released first, this build takes the next number.
Then agent-cadence takes the release into its own copy (vendors it), wires the rule into its merge check, and its
techlead is told which release carries it. ShiftLead needs no change to its commit title.

**Options set aside.** No carve-out at all (every press waits on a reader for a two-line change the rule can check
whole); trusting the existing safety check alone (the pull request would choose its own form and could change
other files); allowing only the answered-item state (most presses would go to review); folding it into today's
rule (that changes the reasons it gives its callers); refusing an entry the person owns, as the button does (that
is ShiftLead's policy, not the format's).

**The rounds.** Six rounds to the cap, then two more that Paul bought. Round 7 found one problem that would change
the build (a test case for over-long entry numbers that the build's own grammar test would fail on), fixed. Round 8
began by moving the release to v3.3, since v3.2 was released; its fact-check found that a release note shared with
TD-119's build would contradict itself, so each build now writes its own. Its design review read the whole plan,
round 7's fixes among them, and found nothing that would change the build, only six smaller points: how the new
test cases are laid out, that a person missing from the board's list of people reads as no question asked, and
that the build waits for TD-119's matching wording. Three topics kept coming back over the rounds: how far the trust
reaches, the release number, and text that cannot be read. Round 8's reviewer judged the first sound, the second
now only a matter of the two plans agreeing, and the third settled.

**The recommendation is Go:** the grinders build it once TD-119's round has merged. One more round would read only
round 8's small fixes, none of which changes what is built. Hold with a note would stop it and have a session revise
the design as the note says.
