# TD-058: v2.7, the Status release, and `migrate`

v2.7 finishes moving every ledger to the v2 form. It ships `migrate`, which rewrites a ledger's old forms into the
new ones in one commit. It then makes any Status outside four forms an error on every entry.

**The four forms.** An open entry's Status is `Open` and nothing else. An archived entry's is `Resolved <date>`,
`Superseded <date> by <id>` or `Dropped <date>`. Anything else, or no Status, is an error. The error names the
word it found and what replaces it, and ends by pointing at `migrate`. A reader still reads another repo's old
words, so a repo that has not migrated yet does not break its neighbours.

**What `migrate` does to each entry:**
- **An archived entry's Status** becomes one of the three archived forms, dated by its own date, its
  `**Resolved:**` line or the archiving date the caller passes. For example `Done` and `Built` become `Resolved`,
  `OBE` becomes `Dropped`, and `Moved to TD-5` becomes `Superseded … by TD-5`. When it cannot map a word or find
  a date, it stops, writes nothing, and lists each such entry. A person then answers each with
  `--as TD-n=resolved|dropped|superseded <id>`.
- **An open entry's stage word** (`Designed`, `Built`, …) or prose becomes `Open`, and the old text is kept as a
  dated `was:` Log line. It sets `Kind` only when the caller says which stage means which kind, because those
  words belong to the consumers. An open entry whose Status says it is finished (`Done`, `Resolved`) stops
  `migrate` rather than being offered as work again. A person archives it or answers `open`.
- **Notes and comments.** The notes after a Status's word and a comment after an `Added` date move into the Log,
  in date order. A note is only moved when every date it would carry is a real calendar day.
- **`Location`** moves from the header into the body, where `edit` already puts that section.
- **What it leaves alone:** `Waits`, `Taken by`, the old decision form and every Log line already there. An entry
  that needs no change is left exactly as it is, even one whose text has some other fault (it is listed). If
  such an entry does need a change, `migrate` stops on it.

It never writes a Status or a Log line that `check()` would reject. Run twice, it changes nothing. A dry run and
`--plan` show every change first.

**Work it re-blocks or releases.** Today an archived `OBE` or `Moved` entry counts as finished, so work waiting on
it is free to pick. After `migrate` it is `Dropped`, which keeps that work waiting, or `Superseded`, which frees it
only when its successor is finished. A prose Status answered `resolved` frees work the other way. `migrate` lists
each open entry whose blocker changes like this, so the person sees it before the commit. It never stops on it.
Another repo that reads this archive sees the same change once this repo migrates, and this listing cannot show
it. An archived `Moved to` naming only the entry itself becomes `Dropped`, and a `Superseded` by itself stops
`migrate` unless it is already in its final form.

**Other parts of v2.7:**
- `new --location` writes the body section.
- `set` refuses a non-empty header `Location` (an empty one still removes the field).
- A header `Location` that an edit writes is an error. One already there is a notice. Until an entry is migrated,
  `reopen` and `renumber` refuse it when it has a header `Location`, and `renumber` refuses it when its Status
  is outside the set.
- SPEC's grammar appendix gains the entry header and the Log's lines.
- `migrate` stays through every v2.x and goes in v3.0. Before v3.0, no repo's dry run may show an entry with
  changes, and no entry may still hold one of the old forms `migrate` leaves. v3.0's own design decides how archived entries
  lose those.

**The roster path.** This PR also amends the target design's order of moves, as Paul's note asked. It marks the
release table agreed and folds the old renaming notes into it. It drops the line that held v2.7 until every repo
had converted its `Waits` lines. Each of the
four roster repos gets one remodel when it moves to v2.7, doing the old v2.4 steps and the v2.7 ones together.
The quiet repos go first. That bump also brings a long agent-cadence jump.

**How it is built:** five builds in series. B0 is the header order and `Location`. B1 is `migrate_entry()`. B2
is the `ledger.py migrate` command. B3 turns the error on and migrates this repo's own ledger. B4 is the grammar
appendix. Each build lands its SPEC text with its code.
