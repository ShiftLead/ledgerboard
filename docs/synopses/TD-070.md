# TD-070: the board as a directory, for v3.0

Today the board is one Markdown file, with one long line per item. This scope draft proposes that v3.0 turn it into
a directory with one file per item, the way the ledger became a directory in v2. It is a scope for your answer,
with no SPEC text or review rounds yet.

**Why.** Two PRs that each add an item always conflict, because every new item is written at the same place in the
file. Those conflicts are real but rare: about 7 counted against roughly 140 on the old one-file ledgers. They are
not the main reason. The main reason is that a `decide` item now has an entry's shape: a line of up to a kilobyte, a detail
block, and a life from open through decided and closed to archived. As one line, that shape brings three costs:
- Its identity is its own text (the item key), which consumers store, so every new field must decide whether it
  changes that identity.
- Its fields sit inside prose, so writers refuse any words that look like a field name.
- An open and a closed copy of the same line is how a merge marks it closed, so archiving needs its own bulk step
  and its own rules. This repo's board holds 32 closed items that were never archived.

**What it proposes.**
- **Do it** in v3.0. Keeping the single file, with agent-cadence's `replay` tool easing the rebases, is the
  alternative. The design would record why if you choose that.
- **An id per item**: its date and a random 8-hex nonce (`2026-11-11-3f9a2c1d`), which names its file and replaces
  the item key. A counter like the ledger's was rejected, because every item would need a push to the counter
  branch.
- **Each item file is a small entry**, not the old line. It has header fields (`Kind`, `Context`, `Due`,
  `Answers`, `Decided`, …), the detail block as its body, and replies as Log lines. That removes the item key,
  the field-name refusals and the Context-end parsing. The cheaper alternative keeps today's line as the file's
  first line. It needs less building but keeps the line's costs.
- **The layout** is `docs/user_attention/`. It has a `README.md` holding the preamble (`People:`,
  `Answered by:`), one file per open item, and `archive/<YYYY-MM>/`. Closing an item moves its file into the
  archive in the same write, which retires bulk archiving, `ARCHIVE_AT` and the twin rule. The month folders let
  the gate sweep read only recent months. The `## Needs the user` and `## In-flight` sections go, because the
  item's kind carries what they meant.
- **One reader for either major**, so a consumer can vendor v3.0 before it migrates. The writers write only the
  new form.
- **The writers and the merge gate** name items by id instead of line. The answer carve-out becomes one item
  file changed, or moved to the archive when the answer closes it.
- **What you read**: `board.py show` prints the board as one text in priority order. No rendered file is
  stored, because every write would touch it.
- **Migration**: `split_board()` converts a v2 board and its archive. Each item's id comes from its date and a
  hash of its old key, so a consumer can map every key it stored. It runs in each consumer's v3.0 vendor PR.
- **The consumers**: agent-cadence's board tooling and ShiftLead's stored keys and forge reads each change in
  their own v3.0 vendor entry.

**What it would build.** Five builds, sketched: the item file and its id, the reader, the writer, the merge
gate's verdicts, and the migration. The rounds settle the exact cut.

**Your choices.** Whether to do it at all (S1). The id's form (S2). The entry-shaped item file against keeping
the line in a file (S3), which is the largest choice. Dropping the sections (S4).
