# TD-070: the board as a directory, for v3.0

Today the board is one Markdown file, one line per item. In v3.0 it becomes a directory, one file per item, as the
ledger did in v2. Two PRs that each add an item always conflict, but the main reason is the item's shape: a `decide`
item is a line of up to a kilobyte, with a detail block and a life from open to archived. On one line that costs
three things. The item's identity is its own text (the item key), which consumers store, so every new field must
decide whether it is in the key. Its fields sit inside prose, so the writers refuse any words that look like a field
name. And an open and a closed copy of one line is how a merge marks it closed, so archiving needs its own bulk
step, which nobody owes: this repo's board holds 36 closed items. Paul said **Go** to the scope (S1–S10); every
recommendation in it stands.

**The id.** Each item has an id: its `Added` date and eight random hex digits, such as `2026-11-11-3f9a2c1d`. It
names the item's file and never changes: a retitle, an edit and a close keep it. `board.py add` draws it. A caller
may pass its own (`--id`), refused if malformed, held, or not of the item's date. A counter like the ledger's was
rejected: every item would need a push.

**The item file.** Each item is a small entry. Its `## ` heading is the item's words. Its header holds the fields
(`Kind`, `Added`, `Context`, `Due`, `Answers`, `Decided`, `Closed` and the rest), its body the detail block, and its
`**Log:**` the replies. Each value is a whole line, so it can hold any words, field names among them. `Decided`
reads `<date>[ by <person>] — <label>` and `Closed` reads `<date>[ — <why>]`, so an answer may now end in `(by …)`.
A value not in its form is kept but read as absent: a `Kind` outside the five makes the item a to-do, so it is still
shown. An unknown field is kept, but the gate faults it, so a consumer writes a new field only once every reader of
its board runs that release.

**The layout.** `docs/user_attention/` holds `README.md` (the opening prose, `Ledgerboard: 3`, `People:`,
`Answered by:` and the stamps), one `<id>.md` per open item, and `archive/<YYYY-MM>/<id>.md` for a closed item,
filed under the month of its `Closed:` date. Closing an item (`done`, or a `decide` that closes) moves its file in
the same write. Nothing else moves a file, and no writer edits a closed item. **No sections:** `## Needs the user`,
`## In-flight` and `add --under` go. Neither consumer reads a section for its meaning, and the kind says what the
one audit that reads a heading stood for. **README's stamps stay a shared file:** every sweep that stamps rewrites
`README.md`, so two stamps can still conflict there. That is a known limit of v3.0. Moving stamps out is the
consumer's choice, open to it later.

**What v3.0 drops.** The item key as what an item is (`item_key()` stays only to read v2 lines and make their ids).
The open-and-closed twin rule, except when reading a v2 board. Bulk archiving (`archive_closed()`, `ARCHIVE_AT`,
`board.py archive`). The v2 line writers, and with them the refusal of field names in a text, context, answer,
detail or reply. And the edits' `--line` and `--expect`: every edit names its item by `--id`.

**Reading.** `load_board()` reads either major, so a consumer can vendor v3.0 before it splits its board, and can
read other repos' boards in either form. A v2 item reads with the same id its split file gets, and a v2 board reads
the same items as its split. Two things read differently on a v2 board: an open line whose closed twin is in the
archive is now closed (v2.x read two items), and a board file declaring no major reads as 2. Damaged input never
raises: one numbered list of rules says what is skipped or read anyway, and `board_dir_problems()` names it all. A
`since` date lets a reader skip old archive months, but only one that judges open items and recent closes. The
writers write v3 only: a write to a v2 board is refused with *split first*. **What you read:** `board.py show`
prints what needs you, in order, each item under a line with its id and class (`--hidden` adds the hidden ones). No
rendered file is stored: every write would touch it.

**The stub.** After the split, `docs/user_attention.md` is a stub declaring `Ledgerboard: 3`. A v3 reader or writer
given that path uses the directory beside it. A v2.x reader that checks the version refuses it, and a v2.x writer
refuses it unread, so neither reads an empty board or forks a new one. A repo splits only once every reader of its
board runs v3.0.

**Tie order changes at the split.** Where items tie for the person's attention (undated, `fyi`, or the same day), a
v2 board keeps its line order and a v3 board orders by id, newest first, at random within one day. So tied items can
change order when a board is split. Which items need the person, their classes and their days do not change.

**The gate sweep** reads each board whole, every archive month. A window was dropped: an owed answer and the
`; board <repo>` audit can reach a closed item of any age. Since no writer edits a closed item, a consumer may cache
each archive file by its path and blob sha and fetch only what is new. A tighter bound can come in a v3.x minor if
the cost ever shows.

**The merge gate's verdicts over a directory.** The verdicts judge what changed between the base's and head's trees,
never how a forge reports a move. A lift's board test is that its only board change is one item's file, edited in
place or moved into the archive, exactly as the writer would write it. A lift on a v2 board, and the split PR
itself, take ordinary review. The item gate (`board_problems()`) judges an item once, when it is added; damage a
hand edit does later is `board_dir_problems()`'s, which each consumer's checks call.

**Migration.** `board.py split` turns a v2 board and its archive into the directory and leaves the stub. Each item's
id is its date and the 8 hex digits of the hash ShiftLead's work orders store, so a stored `board:<8 hex>` finds its
item by the id's last 8 digits, open or closed. Twins become one closed item. The split refuses prose among the
items, an undated item, a closed item with no `Closed:` date, two items with one id, and a result that does not read
back the same items. It runs in each consumer's v3.0 vendor PR, when no open PR edits the board.

**`Doer`** is a v3 header field, defined wholly here: on an `act` only, `<repo>` or `team <team>`, written by
`add --doer`. It lands in B1 whatever happens to TD-065. If TD-065 ships in v2.8, its v2 `Doer:` is read on v2 lines
and carried into the header field at the split. If it is closed as superseded, no v2 line has one.

**After the build.** Five builds, each with its SPEC text, code and fixtures: B1 the item file and its id, B2
reading, B3 the writer and `show`, B4 the merge gate's verdicts, B5 migration and v3.0's removals. Order: B1, B2,
then B3 and B4 either way, then B5. Each leaves `main` green; B5 removes the shims that keep it so. Two
preconditions before B1, both Paul's: decide TD-065 (ship it in v2.8, or close it as superseded), and release v2.8,
carrying whatever `main` holds past v2.7, before B1 merges. **No v2.x release follows once B1 merges**; a v2.x fix
wanted after that goes into v3.0. After B5: v3.0's release with TD-078's ledger half (when, and what else it
carries, is Paul's), this repo's own split, and each consumer's entry, agent-cadence's first, then ShiftLead's.

**The rounds.** Six rounds, ending at the cap. Build-changing findings per design review: 12, 4, 3, 5, 3, 4. Per
fact-check: 2, 2, 1, 0, 0, 0, and the closing fact-check found 1. Three topics kept coming back. **Tie and list
order:** one order is stated once, and two reads of one board are compared by their items, never their order. **The
build-by-build shims:** round 5 kept a v2 item's old `text` beside its new `words` from B2 to B5, replacing round
4's single accessor and grep check. **Doer and TD-065:** round 5 gave `Doer` its own value reader and made deciding
TD-065 a precondition of B1, replacing round 4's rule that B1 reuse TD-065's names if they had landed. Round 6's
design review judged all three ended. **Not yet read by any design review:** round 6's fixes (F73–F80: named readers
for a v3 item's values, the archive's month layout, `split` without `--to`, unreadable values read as absent, and
