## The problem

Target design §7.4's last bullet: "Fixtures carry the release they apply to, so a consumer can run the set for its own pin (CommonMark publishes its tests per spec version)." Today nothing in `fixtures/` names a release. The package does: each `ledgerboard/*.py` starts `# ledgerboard v<x.y> sha256:<hex>`, stamped by `release.sh` and checked by `fixtures/run.py --check-header`, so a vendored copy proves which release it is. A copy of the fixtures proves nothing. A consumer or another-language reader holding a set cannot tell which release's outputs it expects, or whether it was edited after that release, and a consumer that upgrades its package but not its fixtures (or the reverse) runs one release's module against another's expectations without being told.

## Options weighed

**(a) A release key on each case** (`"release": "<x.y>"` in each `cases.json` case and each directory case's `cmd.json`, plus a sidecar for the `ledger/`, `board/` and `archive/` cases, which have no JSON input to carry it), and `run.py --release <x.y>` running the cases at or below the pin. Rejected, on three counts.
- *Which release it names cannot be kept true.* Most expected files bundle several functions' outputs: a `board/<case>.json` holds `item_record()`, `item_key()`, `closed_items()`, `needs_you()` (v2.3) and `board_people()` (v2.3). A case's expectation changes whenever any function it covers changes, and `run.py --write` rewrites every expected file at once. A tag naming the release that *added* the case then lies (every `board/` case now expects `needs_you` and `people`, v2.3's outputs, so a case added before v2.3 and tagged with its own release fails against that release's module). A tag naming the release that *last changed* its expected output is true only if every `--write` bumps it, which nothing in a file can check without history.
- *An older pin gets little coverage.* Under "last changed", nearly every case moves to the newest release each time a function it touches gains an output, so `--release 2.2` would run few cases.
- *It stores what git already has.* The cases at their release's tag are exactly the set for that release.

**(b) A directory per release** (`fixtures/v2.3/`, `fixtures/v2.4/`, …). Rejected: it copies about 1,800 files each release to keep what the tags already keep, and the copies drift unless every old one is frozen.

**(c) The set carries its release, as the package does (chosen).** One file, `fixtures/MANIFEST`, names the release and lists the sha256 of every other file in the set. `release.sh` stamps it when it stamps the headers, and `run.py --check-header` checks it beside them: intact, and the same release as the package. This is CommonMark's model, a test set per spec version, not a version per test. A consumer runs the set its pin ships, and its vendor check proves the set and the package are one release. An older release's set is its tag's.

The four questions in TD-040's Fix, answered:
1. *How a case names its release:* it does not. The set does, in `fixtures/MANIFEST`.
2. *Added, or last changed:* neither. The set's release is the one whose module wrote every expected output in it.
3. *How `run.py` runs the set for a pin:* by running the set that pin ships (a vendored copy, or the tag's `fixtures/`); `--check-header` proves the set and the package it runs against are one release. There is no `--release` option and no subset.
4. *The existing cases:* nothing is tagged per case. The first stamp is v2.4's. A set from before v2.4 carries no manifest; its release is its tag's.

**On §7.4's cross-version bullet.** "a v2.4 reader (whose fixtures stay in the suite) …" does not need a newer set run against an older module. A reader's behaviour on text from a newer minor is tested in the reader's own set with invented words that no release defines (TD-039's planned `fixtures/ledger/unknownstatus`, word `Xyzzy`, in PR #108), so each release's set stays self-contained.

## The rules

1. **The file.** `fixtures/MANIFEST`, UTF-8, every line ending in LF, the last included.
   - Its first line is `# ledgerboard v<x.y> fixtures`, where `<x.y>` is `<major>.<minor>`, each a run of ASCII digits (`[0-9]+`, not Python's `\d`, which also matches other scripts' digits; leading zeros are accepted, as `release.sh` accepts them).
   - Each later line is `<sha256>  <path>`: 64 lower-case hex digits, two spaces, then the path, as `sha256sum` writes them. A reader splits it at that fixed offset, so the path is everything after the 66th character, spaces included (`a b.md`, `a  b.md`); a line with an empty path, or whose first 66 characters are not that form, is malformed. There is one line per file in the set, and no other line.
   - **The set** is every regular file under `fixtures/`, at any depth, except `fixtures/MANIFEST` itself and anything under a directory named `__pycache__`: such a directory is pruned from the walk, so nothing under it is looked at, while a file that is itself named `__pycache__` is an ordinary member of the set, and a symbolic link named `__pycache__` is a link: it is refused as `not a regular file` (rule 3), the link test coming before the pruning. "A path with a `__pycache__` part" below means this: a directory part, never the last part. `run.py` is in the set. The walk follows no symbolic link (`os.walk(followlinks=False)`, or the same in another language), so a linked directory is not entered; `os.walk` puts a link to a directory in its `dirnames` and a link to a file, a FIFO or a socket in its `filenames`, so both lists are checked (`os.path.islink` on each `dirnames` entry, a regular-file test that follows no link on each `filenames` entry, `stat.S_ISREG(os.lstat(path).st_mode)`; `os.path.isfile` follows links and would list a link to a file as one). The top-level entry named `MANIFEST` is left out of the walk whatever its kind, so a `MANIFEST/` directory is not entered (it is rule 3's `MANIFEST is not a file`). Any entry under `fixtures/` that is neither a directory nor a regular file (a symbolic link to a file or to a directory, a FIFO, a socket, a device) is refused (rule 3), as is a name that is not valid UTF-8. A directory is not in the set itself, so an empty directory adds nothing (git cannot hold one).
   - `<path>` is the file's path relative to `fixtures/`, its parts joined by `/`, its bytes as the file system gives them, with no Unicode normalisation. No path in the set holds a newline, a carriage return or a backslash (rule 3 refuses one), so no escaping is needed.
   - The lines are sorted by `<path>`'s UTF-8 bytes, so `a-b` sorts before `a/b` (`-` is 0x2D, `/` is 0x2F) and `B` before `a`.
   - `<sha256>` is of the file's bytes as stored, untranslated (`.gitattributes` already keeps `fixtures/**` byte for byte, `-text`), so a CRLF fixture hashes its CRs. The manifest is under the same rule, so a checkout never rewrites its LFs.
   - Below its first line the file is `sha256sum` output, so a reader with no Python can check the set with `tail -n +2 MANIFEST | sha256sum -c` from `fixtures/` (that checks only the listed files; the added-file and order checks are `run.py`'s).
   - **Vendoring.** The set is vendored whole and unmodified, at any path: every path is relative to the directory that holds `MANIFEST` (`run.py`'s `HERE`). A consumer's own cases live outside it, and so do its tools' caches and scratch files (a `.pytest_cache`, a `.DS_Store`, an editor's swap file): only `__pycache__` is left out of the set, so anything else in the vendored directory is reported as added; a file added to it or dropped from it is reported (rule 3) and the check fails until the set is restored. The consumer's vendored path needs the same `-text` attribute (or none of its tools converting line endings), or a checkout that rewrites CRLF fixtures or the manifest fails every hash it touches; a formatter run over it (on `run.py` too, which is in the set) fails it the same way.
2. **Writing it.** `run.py --stamp <x.y>` writes `fixtures/MANIFEST` for the set beside it (`HERE`) and prints `stamped fixtures v<x.y> (<n> files)` to stdout, exit 0. `--stamp`, `--check-tracked`, `--check-header` and `--write` are mutually exclusive (argparse's mutually exclusive group; two of them exit 2 with argparse's usage error). That is a change: today `--check-header --write` runs the check and ignores `--write`, and from the build it exits 2; `--stamp` and `--check-tracked` read no package, so `--module` beside either exits 2 too (`--module is not used with --stamp` or `… with --check-tracked`, stderr). The exit-2 errors are checked in this order and only the first is printed: argparse's, then `--module`, then `<x.y>`. A `<x.y>` that is not two dot-separated runs of ASCII digits exits 2 with exactly the line `usage: --stamp <major.minor>` on stderr. Both of `--stamp`'s own exit-2 lines are printed directly, not through `ap.error()` (which would add argparse's usage block); argparse's own errors (two exclusive modes) keep argparse's form. To tell a passed `--module` from none, its default becomes `None`, resolved to `HERE.parent / "ledgerboard"` when absent, as today. A `MANIFEST` entry that is not a regular file also refuses the stamp, exit 1, `fixtures: MANIFEST is not a file`. A set that rule 3's on-disk checks refuse (a non-regular entry, a non-UTF-8 name, a path with a newline, CR or backslash) exits 1, printing each such problem with its `fixtures: ` prefix to stderr (as `--check-tracked` does; only `--check-header` prints its problems to stdout, as it does today). Either way nothing is written and a manifest already there is left as it was. The write is atomic: the text goes to a temporary file in `fixtures/` (whose name begins `.MANIFEST.`, removed on any exception; only a kill between its creation and the replace can leave one, which `--check-header` then reports as added), replaced over `MANIFEST` with `os.replace`; the set is listed before that file exists.

   `release.sh <x.y>` runs it after stamping the headers and before its checks (no step of `release.sh` edits `fixtures/`, so the order against the header stamp does not matter; the stamp must come after anything that would). It then checks that the set is what git tracks, and restores the manifest if not. These are its exact lines, right after the header-stamping Python step (the release branch's, after the `--tag` branch has exited) and before the `python3 fixtures/run.py --check-header` line that follows it:

   ```bash
   python3 fixtures/run.py --stamp "$v"
   if ! (cd fixtures && git ls-files -z) | python3 fixtures/run.py --check-tracked; then
       if git ls-files --error-unmatch fixtures/MANIFEST >/dev/null 2>&1; then
           git checkout -q -- fixtures/MANIFEST
       else
           rm -f fixtures/MANIFEST
       fi
       exit 2
   fi
   ```

   `(cd fixtures && git ls-files -z)` gives git's tracked paths relative to `fixtures/`, NUL-separated and raw (`-z` never quotes or escapes a name, so a non-ASCII name compares as itself); `run.py` reads them on stdin and runs no git itself. `--check-tracked` first checks the manifest file: on any of `manifest_file_problems()` (rule 4) it prints each, `fixtures: <problem>`, to stderr and exits 1. Otherwise it reads stdin as bytes, splits it at each NUL (a trailing empty piece dropped), decodes each path with `os.fsdecode` as the walk does, and compares those paths, less `MANIFEST` and less any path with a `__pycache__` directory part (rule 1), with the paths `manifest_entries()` gives; it prints `fixtures/ differs from what git tracks: <path>` to stderr for each path in one but not the other, sorted by the path's bytes (`os.fsencode`), `<path>` written as its `repr` when it is not valid UTF-8 or holds a newline, a carriage return or a backslash (rule 3's odd names), else as it stands, and exits 1 if there is any, else 0. The `if !` form is needed: under `set -euo pipefail` a bare failing pipeline would stop `release.sh` with exit 1 before the restore. On a failure the manifest is put back as it was (checked out when tracked, from v2.5's release on; else removed, the first release's case) and `release.sh` exits 2. The branch is already cut and the headers stamped then, and they are left so, as when any of `release.sh`'s later checks fails today. A `--stamp` that exits 1 (a refused set, its problems on stderr) stops `release.sh` with exit 1 at that line. (Without the tracked check an ignored or untracked file would be hashed and never committed, and the tag would report it missing.) Then, in place of today's commit line, it adds and commits the manifest with the package, these two lines exactly:

   ```bash
   git add fixtures/MANIFEST
   git commit -qm "Release v$v" -- ledgerboard fixtures/MANIFEST
   ```

   (the add is needed: the first release's manifest is untracked, and a commit pathspec naming an untracked file fails). It commits nothing else. Between releases the manifest is left as it is, as the headers are; a PR that changes a fixture does not restamp it.
3. **Checking it.** `run.py --check-header` checks the package's headers, as today, and then the manifest of the set beside it, everything to stdout. It prints the header line as today (`header: ok (v<x.y>)` or `header: <why>`), then either `fixtures: ok (v<x.y>, <n> files)` or one line per problem, in this order, each starting `fixtures: `:
   - `no MANIFEST — this set names no release (a set from before v2.4 is its tag's)`, when there is no entry named `MANIFEST`; `MANIFEST is not a file`, when it is a directory, a symbolic link or anything else not a regular file; nothing more is checked.
   - `MANIFEST is not UTF-8 text with LF line endings and a final LF`, when its bytes are empty, do not decode as strict UTF-8, hold a CR anywhere, do not end in LF, or hold an empty line (two LFs in a row); nothing more is checked. Otherwise the text is split on LF only, the final empty piece dropped.
   - `MANIFEST's first line is not a release line: '<line>'` (the line as Python's `repr` of the decoded text gives it); nothing more is checked.
   - `MANIFEST line <n> is not '<sha256>  <path>': '<line>'`, for each malformed later line (`<n>` counts from 1, the release line being 1); `MANIFEST lists <path> twice` for each later line whose path equals an earlier well-formed line's; and `MANIFEST line <n> is out of order` for each other well-formed line whose path sorts before the previous well-formed line's. A line listing a path twice is skipped: it is not the previous line for the next one. A path listed twice gives only the first of those two. These are reported line by line, in line order; the checks below then run over the well-formed lines, the first of each path counting. A malformed line lists no path, so a file it was meant to list is also reported as added.
   - `<path>: not a regular file`, `<path>: a name that is not UTF-8` and `<path>: a path holding a newline, a carriage return or a backslash`, for each such entry under `fixtures/` on disk. In these three, and only these, `<path>` is Python's `repr` of the relative path (`os.fsdecode` of its bytes, parts joined by `/`), so a newline or a bad byte cannot break the line; elsewhere `<path>` is written as it stands. They are sorted by the relative path's bytes (`os.fsencode`), and an entry that meets several gets one line, the first of the three in this order; such an entry is not a file of the set, so it is not also reported as added.
   - `<path>: in MANIFEST but missing`, `<path>: not in MANIFEST — added after its release`, and `<path>: its sha256 does not match MANIFEST — edited after its release`, the three kinds merged into one list in path order.
   - When `headers_problem(module)` is `None` and the manifest has no problem above: `MANIFEST names v<a>, the package v<b>` if they differ, `<b>` read as `--check-header` reads it today (the first package file's header).

   It exits 1 when the header or the manifest has any problem, else 0. A manifest is checked only by `--check-header` (run by `release.sh` before both its commit and its tag, and by a consumer's vendor check); a plain run (`python3 fixtures/run.py`) reads no manifest, so the repo's precheck, which runs between releases, is unchanged.
4. **One definition.** The manifest is five functions of `run.py`, which `--stamp`, `--check-tracked`, `--check-header` and the tests share: `manifest_text(root: Path, release: str) -> str`, which raises `ValueError` carrying the on-disk problems when the set has any; `manifest_file_problems(root: Path) -> list[str]`, the problems of rule 3's first four bullets (the manifest file itself: from `no MANIFEST` through its malformed, duplicate and out-of-order lines); `manifest_problems(root: Path) -> list[str]`, those followed by the on-disk and file problems of the next two bullets, which is every problem above but the mismatch (each without the `fixtures: ` prefix); `manifest_entries(root: Path) -> list[tuple[str, str]]`, the `(sha256, path)` of each well-formed later line, the first of each path, in file order, and `[]` when the file has a problem that stops the check (no manifest, not a file, not LF text, a bad first line); and `manifest_release(root: Path) -> str | None`, the `<x.y>` of the first line when `manifest_file_problems()` is empty, else `None`; `--check-header` compares it with the package's only under rule 3's last bullet's condition (no problem at all, and intact headers). `release.sh` writes no manifest of its own. Nothing goes into the package: `ledgerboard/` neither reads nor writes `fixtures/`.

## The cases

The manifest is the runner's, not the module's, so its cases are unit tests in `tests/test_release.py`, each over a set built in a temporary directory (a copy of `run.py` and a few invented files), with `manifest_text()` and `manifest_problems()` imported from that copy:

1. Stamp then check: no problem; `--check-header` against an intact package of the same release prints `fixtures: ok (v<x.y>, <n> files)` and exits 0.
2. The text, pinned byte for byte, of `manifest_text()` over a set of four files (no `run.py`: the function takes its root): `a/b.json`, `a-b.md`, `B.md` and `crlf.md`, whose bytes are `x\r\n`. It is the release line, then the lines in the order `B.md`, `a-b.md`, `a/b.json`, `crlf.md`, the last hashing `x\r\n` with its CR.
3. A file under `__pycache__/` is neither listed nor reported as added; a regular file named `__pycache__` is listed; a symbolic link named `__pycache__` is `not a regular file`.
4. Each problem of rule 3, one test each, with its exact text: no manifest; a bad first line; a malformed line; an out-of-order line; a path listed twice (the one `lists … twice` line, no out-of-order line, and the line after it compared with the line before it); a manifest with CRLF endings, one with no final LF, an empty one and one with a blank line (each the one `not UTF-8 text …` line); `MANIFEST` as a directory; a malformed line beside an edited file (both reported); a missing file; an added file; an edited file; a symbolic link to a file and one to a directory (each `not a regular file`, the directory not entered); a `MANIFEST/` directory holding a file (only `MANIFEST is not a file`, its file not reported as added); a fixture whose name is not ASCII (`é.md`), listed and checked as itself; a FIFO (skipped where `os.mkfifo` is missing); a name that is not UTF-8, a name holding a newline (its `repr` pinned, `'a\nb.md'`, a backslash and an `n` in the output), and a path holding a backslash (each skipped where the file system refuses one); a name both not UTF-8 and holding a backslash, which gets only the `not UTF-8` line; and the release mismatch (a package stamped v2.3, a manifest v2.4).
5. The mismatch is not reported while either side has another problem.
6. `--stamp 2` and `--stamp v2.4` exit 2 with the usage line and write nothing; `--check-header --write`, `--stamp 2.4 --check-header`, `--stamp 2.4 --write` and `--stamp 2.4 --module x` exit 2, the last with exactly `--module is not used with --stamp`; `--stamp 2 --module x` prints only the `--module` line (the order of rule 2); `--stamp` over a `MANIFEST/` directory exits 1; `--stamp` over a set holding a symbolic link exits 1 with its problem and leaves an existing `MANIFEST` byte for byte as it was; and a successful `--stamp` leaves no `.MANIFEST.` file.
6a. `--check-tracked`, over a stamped set: stdin naming exactly its files (with `MANIFEST` and a `__pycache__/x.pyc` among them) exits 0; stdin missing one file, and stdin naming one extra, each exit 1 with that path's `differs from what git tracks` line on stderr; a non-ASCII name given raw compares as itself; a non-UTF-8 path and one holding a newline on stdin are each reported by its `repr`, on one line, and do not raise; a set with no `MANIFEST` exits 1 with `fixtures: no MANIFEST …` on stderr before comparing; `--check-tracked --module x` exits 2 with `--module is not used with --check-tracked`, and `--check-tracked --write` exits 2.
6b. Paths with spaces: a set holding `a b.md` and `a  b.md` stamps and checks clean; a line with an empty path (`<sha256>  `) is malformed.
6c. **The real set.** A test imports the repo's own `fixtures/run.py` and calls `manifest_text(HERE, "0.0")`, which must not raise (no file of today's set is refused); where `git rev-parse --is-inside-work-tree` succeeds in `fixtures/` (so not in an export or a tarball) and `git ls-files` succeeds there, it also runs that `run.py --check-tracked` against a temporary copy of the set stamped there, on the stdin `(cd fixtures && git ls-files -z)` gives in the repo, and expects exit 0 and no output; otherwise that half is skipped, never failed. It writes nothing into `fixtures/`, so a fixture added with a name the stamp refuses, or left untracked, fails the precheck in its own PR rather than mid-release.
7. **The tag.** The existing `ReleaseTag` tests seed a throwaway repo with `release.sh`, `ledgerboard/__init__.py` and `fixtures/run.py`, stamp the header as a release would, and run `release.sh --tag`. Once `--check-header` checks the manifest, that seed has none and every one of them would be refused, so `setUp` also runs the seed's `fixtures/run.py --stamp <version>` before its commit. A new test then edits `fixtures/run.py` in a later commit (pushed, so HEAD is still origin/main) and checks that `release.sh --tag` exits non-zero with `fixtures: run.py: its sha256 does not match MANIFEST — edited after its release` in its output, and creates no tag.
7a. **The block, run.** A test takes rule 2's block out of `release.sh` (its lines from the `--stamp` line through the closing `fi`) and runs it with `bash -c 'set -euo pipefail; v=9.9; <block>'` in a throwaway git repo whose `fixtures/run.py` is a stub: `--stamp` writes a `MANIFEST`, and `--check-tracked` reads stdin to its end (so `git ls-files` never dies of a closed pipe, which `pipefail` would count as a failure) and exits 1. With no tracked manifest it exits 2, prints nothing on stderr but the stub's, and leaves no `fixtures/MANIFEST`; with a committed one it exits 2 and leaves that file as committed. With a stub whose `--check-tracked` reads stdin to its end and exits 0 it exits 0 and leaves the new manifest.
8. **The stamp step.** `release.sh <x.y>` runs the whole suite and the fixtures, which a throwaway seed cannot hold, so its stamp step is pinned by text. A test reads `release.sh`'s lines, leaving out comment lines (those whose first non-blank character is `#`), strips each of leading and trailing blanks, and checks that rule 2's nine-line block appears as consecutive lines, after the header-stamping step and before the `python3 fixtures/run.py --check-header` line that follows the block (`release.sh` has another, in its `--tag` branch, which comes before it), and that rule 2's two commit lines appear consecutively after that check, with no other `git commit` line after the branch is cut. The block and the commit first run for real at v2.4's release, whose `--check-header` (in `release.sh`, before the commit) checks what the stamp wrote.
