# TD-040: the fixtures carry the release they belong to

**Status:** In review 2026-11-04 (the designer). Class: **wide**, because it changes a published, vendored artefact: the conformance set any implementation runs, and what a consumer's copy proves about itself (cap 6 rounds, cadence.md §4.8 *Design review rounds*). The review record is `docs/reviews/TD-040.md`.

**Entry:** [TD-040](../ledger/TD-040.md), split off TD-035 on Paul's answer of 2026-11-04.

## The problem

Target design §7.4's last bullet: "Fixtures carry the release they apply to, so a consumer can run the set for its own pin (CommonMark publishes its tests per spec version)." Today nothing in `fixtures/` names a release. The package does: each `ledgerboard/*.py` starts `# ledgerboard v<x.y> sha256:<hex>`, stamped by `release.sh` and checked by `fixtures/run.py --check-header`, so a vendored copy proves which release it is. A copy of the fixtures proves nothing. A consumer or another-language reader holding a set cannot tell which release's outputs it expects, or whether it was edited after that release, and a consumer that upgrades its package but not its fixtures (or the reverse) runs one release's module against another's expectations without being told.

## Options weighed

**(a) A release key on each case** (`"release": "<x.y>"` in each `cases.json` case and each directory case's `cmd.json`, plus a sidecar for the `ledger/`, `board/` and `archive/` cases, which have no JSON input to carry it), and `run.py --release <x.y>` running the cases at or below the pin. Rejected, on three counts.
- *Which release it names cannot be kept true.* Most expected files bundle several functions' outputs: a `board/<case>.json` holds `item_record()`, `item_key()`, `closed_items()`, `needs_you()` (v2.3) and `board_people()` (v2.3). A case's expectation changes whenever any function it covers changes, and `run.py --write` rewrites every expected file at once. A tag naming the release that *added* the case then lies (every `board/` case now expects `needs_you` and `people`, v2.3's outputs, so a case added before v2.3 and tagged with its own release fails against that release's module). A tag naming the release that *last changed* its expected output is true only if every `--write` bumps it, which nothing in a file can check without history.
- *An older pin gets little coverage.* Under "last changed", nearly every case moves to the newest release each time a function it touches gains an output, so `--release 2.2` would run few cases.
- *It stores what git already has.* The cases at their release's tag are exactly the set for that release.

**(b) A directory per release** (`fixtures/v2.3/`, `fixtures/v2.4/`, …). Rejected: it copies about 1,800 files each release to keep what the tags already keep, and the copies drift unless every old one is frozen.

**(c) The set carries its release, as the package does (chosen).** One file, `fixtures/MANIFEST`, names the release and lists the sha256 of every other file in the set. `release.sh` stamps it when it stamps the headers, and `run.py --check-header` checks it beside them: intact, and the same release as the package. This is CommonMark's model, a test set per spec version, not a version per test. A consumer runs the set its pin ships, and its vendor check proves the set and the package are one release. An older release's set is its tag's.

The four questions in TD-040's Fix, answered:
1. *How a case names its release:* it does not. The set does, in `fixtures/MANIFEST`.
2. *Added, or last changed:* neither. The set's release is the one whose module wrote every expected output in it.
3. *How `run.py` runs the set for a pin:* by running the set that pin ships (a vendored copy, or the tag's `fixtures/`); `--check-header` proves the set and the package it runs against are one release. There is no `--release` option and no subset.
4. *The existing cases:* nothing is tagged per case. The first stamp is v2.4's. A set from before v2.4 carries no manifest; its release is its tag's.

**On §7.4's cross-version bullet.** "a v2.4 reader (whose fixtures stay in the suite) …" does not need a newer set run against an older module. A reader's behaviour on text from a newer minor is tested in the reader's own set with invented words that no release defines (TD-039's planned `fixtures/ledger/unknownstatus`, word `Xyzzy`, in PR #108), so each release's set stays self-contained.

## The rules

1. **The file.** `fixtures/MANIFEST`, UTF-8, every line ending in LF, the last included.
   - Its first line is `# ledgerboard v<x.y> fixtures`, where `<x.y>` is `<major>.<minor>`, each a run of ASCII digits.
   - Each later line is `<sha256>  <path>`: 64 lower-case hex digits, two spaces, then the path, as `sha256sum` writes them. There is one line per file in the set, and no other line.
   - **The set** is every regular file under `fixtures/`, at any depth, except `fixtures/MANIFEST` itself and any file under a directory named `__pycache__`. `run.py` is in the set. The walk follows no symbolic link (`os.walk(followlinks=False)`, or the same in another language), so a linked directory is not entered; `os.walk` puts a link to a directory in its `dirnames` and a link to a file, a FIFO or a socket in its `filenames`, so both lists are checked (`os.path.islink` on each `dirnames` entry, a regular-file test that follows no link on each `filenames` entry, `stat.S_ISREG(os.lstat(path).st_mode)`; `os.path.isfile` follows links and would list a link to a file as one). The top-level entry named `MANIFEST` is left out of the walk whatever its kind, so a `MANIFEST/` directory is not entered (it is rule 3's `MANIFEST is not a file`). Any entry under `fixtures/` that is neither a directory nor a regular file (a symbolic link to a file or to a directory, a FIFO, a socket, a device) is refused (rule 3), as is a name that is not valid UTF-8. A directory is not in the set itself, so an empty directory adds nothing (git cannot hold one).
   - `<path>` is the file's path relative to `fixtures/`, its parts joined by `/`, its bytes as the file system gives them, with no Unicode normalisation. No path in the set holds a newline, a carriage return or a backslash (rule 3 refuses one), so no escaping is needed.
   - The lines are sorted by `<path>`'s UTF-8 bytes, so `a-b` sorts before `a/b` (`-` is 0x2D, `/` is 0x2F) and `B` before `a`.
   - `<sha256>` is of the file's bytes as stored, untranslated (`.gitattributes` already keeps `fixtures/**` byte for byte, `-text`), so a CRLF fixture hashes its CRs. The manifest is under the same rule, so a checkout never rewrites its LFs.
   - Below its first line the file is `sha256sum` output, so a reader with no Python can check the set with `tail -n +2 MANIFEST | sha256sum -c` from `fixtures/` (that checks only the listed files; the added-file and order checks are `run.py`'s).
   - **Vendoring.** The set is vendored whole and unmodified, at any path: every path is relative to the directory that holds `MANIFEST` (`run.py`'s `HERE`). A consumer's own cases live outside it; a file added to it or dropped from it is reported (rule 3) and the check fails until the set is restored. The consumer's vendored path needs the same `-text` attribute (or none of its tools converting line endings), or a checkout that rewrites CRLF fixtures or the manifest fails every hash it touches.
2. **Writing it.** `run.py --stamp <x.y>` writes `fixtures/MANIFEST` for the set beside it (`HERE`) and prints `stamped fixtures v<x.y> (<n> files)` to stdout, exit 0. `--stamp`, `--check-tracked`, `--check-header` and `--write` are mutually exclusive (argparse's mutually exclusive group; two of them exit 2 with argparse's usage error); `--stamp` and `--check-tracked` read no package, so `--module` beside either exits 2 too (`--module is not used with --stamp` or `… with --check-tracked`, stderr). The exit-2 errors are checked in this order and only the first is printed: argparse's, then `--module`, then `<x.y>`. A `<x.y>` that is not two dot-separated runs of ASCII digits exits 2 with exactly the line `usage: --stamp <major.minor>` on stderr. Both of `--stamp`'s own exit-2 lines are printed directly, not through `ap.error()` (which would add argparse's usage block); argparse's own errors (two exclusive modes) keep argparse's form. To tell a passed `--module` from none, its default becomes `None`, resolved to `HERE.parent / "ledgerboard"` when absent, as today. A `MANIFEST` entry that is not a regular file also refuses the stamp, exit 1, `fixtures: MANIFEST is not a file`. A set that rule 3's on-disk checks refuse (a non-regular entry, a non-UTF-8 name, a path with a newline, CR or backslash) exits 1, printing each such problem with its `fixtures: ` prefix to stdout. Either way nothing is written and a manifest already there is left as it was. The write is atomic: the text goes to a temporary file in `fixtures/` (whose name begins `.MANIFEST.`, removed on any exception; only a kill between its creation and the replace can leave one, which `--check-header` then reports as added), replaced over `MANIFEST` with `os.replace`; the set is listed before that file exists.

   `release.sh <x.y>` runs it after stamping the headers and before its checks (no step of `release.sh` edits `fixtures/`, so the order against the header stamp does not matter; the stamp must come after anything that would). It then checks that the set is what git tracks: the line `(cd fixtures && git ls-files -z) | python3 fixtures/run.py --check-tracked` feeds git's tracked paths, relative to `fixtures/` and NUL-separated (`-z` gives each name raw, never quoted or escaped, so a non-ASCII name compares as itself), to `run.py`, which reads no git itself. `--check-tracked` compares them, less `MANIFEST` and less any path with a `__pycache__` part, with the paths `MANIFEST` lists; it prints `fixtures/ differs from what git tracks: <path>` to stderr for each path in one but not the other, in path order, and exits 1 if there is any, else 0 (it exits 1 too, `fixtures: <problem>`, on any of `manifest_problems()`' manifest-file problems, before comparing). If it fails, `release.sh` puts the manifest back as it was and exits 2: `git checkout -q -- fixtures/MANIFEST` when `git ls-files --error-unmatch fixtures/MANIFEST` finds the file tracked (from v2.5's release on), else `rm -f fixtures/MANIFEST`. The branch is already cut and the headers stamped then, and they are left so, as when any of `release.sh`'s later checks fails today. `release.sh` runs under `set -euo pipefail`, so a `--stamp` that exits 1 (a refused set, its problems on stdout) stops it with exit 1 at that step. (An ignored or untracked file would otherwise be hashed and never committed, and the tag would report it missing.) Then it adds and commits the manifest with the package: `git add fixtures/MANIFEST` and `git commit -qm "Release v$v" -- ledgerboard fixtures/MANIFEST` (the add is needed: the first release's manifest is untracked, and a commit pathspec naming an untracked file fails). It commits nothing else. Between releases the manifest is left as it is, as the headers are; a PR that changes a fixture does not restamp it.
3. **Checking it.** `run.py --check-header` checks the package's headers, as today, and then the manifest of the set beside it, everything to stdout. It prints the header line as today (`header: ok (v<x.y>)` or `header: <why>`), then either `fixtures: ok (v<x.y>, <n> files)` or one line per problem, in this order, each starting `fixtures: `:
   - `no MANIFEST — this set names no release (a set from before v2.4 is its tag's)`, when there is no entry named `MANIFEST`; `MANIFEST is not a file`, when it is a directory, a symbolic link or anything else not a regular file; nothing more is checked.
   - `MANIFEST is not UTF-8 text with LF line endings and a final LF`, when its bytes are empty, do not decode as strict UTF-8, hold a CR anywhere, do not end in LF, or hold an empty line (two LFs in a row); nothing more is checked. Otherwise the text is split on LF only, the final empty piece dropped.
   - `MANIFEST's first line is not a release line: '<line>'` (the line as Python's `repr` of the decoded text gives it); nothing more is checked.
   - `MANIFEST line <n> is not '<sha256>  <path>': '<line>'`, for each malformed later line (`<n>` counts from 1, the release line being 1); `MANIFEST lists <path> twice` for each later line whose path equals an earlier well-formed line's; and `MANIFEST line <n> is out of order` for each other well-formed line whose path sorts before the previous well-formed line's. A line listing a path twice is skipped: it is not the previous line for the next one. A path listed twice gives only the first of those two. These are reported line by line, in line order; the checks below then run over the well-formed lines, the first of each path counting. A malformed line lists no path, so a file it was meant to list is also reported as added.
   - `<path>: not a regular file`, `<path>: a name that is not UTF-8` (`<path>` here being Python's `repr` of the name as `os.fsdecode` gives it) and `<path>: a path holding a newline, a carriage return or a backslash`, for each such entry under `fixtures/` on disk, in path order; such an entry is not a file of the set, so it is not also reported as added.
   - `<path>: in MANIFEST but missing`, `<path>: not in MANIFEST — added after its release`, and `<path>: its sha256 does not match MANIFEST — edited after its release`, the three kinds merged into one list in path order.
   - When `headers_problem(module)` is `None` and the manifest has no problem above: `MANIFEST names v<a>, the package v<b>` if they differ, `<b>` read as `--check-header` reads it today (the first package file's header).

   It exits 1 when the header or the manifest has any problem, else 0. A manifest is checked only by `--check-header` (run by `release.sh` before both its commit and its tag, and by a consumer's vendor check); a plain run (`python3 fixtures/run.py`) reads no manifest, so the repo's precheck, which runs between releases, is unchanged.
4. **One definition.** The manifest is three functions of `run.py`, which `--stamp`, `--check-tracked`, `--check-header` and the tests share: `manifest_text(root: Path, release: str) -> str`, which raises `ValueError` carrying the on-disk problems when the set has any; `manifest_problems(root: Path) -> list[str]` (every problem above but the mismatch, without the `fixtures: ` prefix); and `manifest_release(root: Path) -> str | None`, the `<x.y>` of an intact manifest's first line, else `None`, which `--check-header` compares with the package's. `release.sh` writes no manifest of its own. Nothing goes into the package: `ledgerboard/` neither reads nor writes `fixtures/`.

## What changes where

- **`fixtures/run.py`:** `manifest_text()`, `manifest_problems()`, `manifest_release()`, `--stamp` and `--check-tracked`; `--check-header` gains the manifest check (rule 3), and its help text says it checks both; the docstring's usage block and its `--check-header` paragraph say so (text below).
- **`release.sh`:** the stamp, the tracked-files check and the wider commit (rule 2); its header comment gains the manifest (text below). `--tag` needs no change: it already runs `--check-header`, which now refuses a manifest edited after the stamp.
- **`fixtures/MANIFEST`:** written once, by v2.4's `release.sh` run, never by the build's PR. The build commits no manifest, so main between the build and the release has none, and `--check-header` on main says so (`no MANIFEST …`); only `release.sh` and a consumer's check run it, and `release.sh` stamps before it checks.
- **`README.md`:** the `fixtures/` bullet gains one sentence (text below).
- **`SPEC.md`:** two passages (below).
- **`docs/plans/target-design.md`:** §7.4's last bullet gains a dated pointer (below).
- **`tests/test_release.py`:** the cases below.

## The cases

The manifest is the runner's, not the module's, so its cases are unit tests in `tests/test_release.py`, each over a set built in a temporary directory (a copy of `run.py` and a few invented files), with `manifest_text()` and `manifest_problems()` imported from that copy:

1. Stamp then check: no problem; `--check-header` against an intact package of the same release prints `fixtures: ok (v<x.y>, <n> files)` and exits 0.
2. The text, pinned byte for byte, of `manifest_text()` over a set of four files (no `run.py`: the function takes its root): `a/b.json`, `a-b.md`, `B.md` and `crlf.md`, whose bytes are `x\r\n`. It is the release line, then the lines in the order `B.md`, `a-b.md`, `a/b.json`, `crlf.md`, the last hashing `x\r\n` with its CR.
3. A file under `__pycache__/` is neither listed nor reported as added.
4. Each problem of rule 3, one test each, with its exact text: no manifest; a bad first line; a malformed line; an out-of-order line; a path listed twice (the one `lists … twice` line, no out-of-order line, and the line after it compared with the line before it); a manifest with CRLF endings, one with no final LF, an empty one and one with a blank line (each the one `not UTF-8 text …` line); `MANIFEST` as a directory; a malformed line beside an edited file (both reported); a missing file; an added file; an edited file; a symbolic link to a file and one to a directory (each `not a regular file`, the directory not entered); a `MANIFEST/` directory holding a file (only `MANIFEST is not a file`, its file not reported as added); a fixture whose name is not ASCII (`é.md`), listed and checked as itself; a FIFO (skipped where `os.mkfifo` is missing); a name that is not UTF-8 and a path holding a backslash (each skipped where the file system refuses one); and the release mismatch (a package stamped v2.3, a manifest v2.4).
5. The mismatch is not reported while either side has another problem.
6. `--stamp 2` and `--stamp v2.4` exit 2 with the usage line and write nothing; `--stamp 2.4 --check-header`, `--stamp 2.4 --write` and `--stamp 2.4 --module x` exit 2, the last with exactly `--module is not used with --stamp`; `--stamp` over a `MANIFEST/` directory exits 1; `--stamp` over a set holding a symbolic link exits 1 with its problem and leaves an existing `MANIFEST` byte for byte as it was; and a successful `--stamp` leaves no `.MANIFEST.` file.
6a. `--check-tracked`, over a stamped set: stdin naming exactly its files (with `MANIFEST` and a `__pycache__/x.pyc` among them) exits 0; stdin missing one file, and stdin naming one extra, each exit 1 with that path's `differs from what git tracks` line on stderr; a non-ASCII name given raw compares as itself.
7. **The tag.** The existing `ReleaseTag` tests seed a throwaway repo with `release.sh`, `ledgerboard/__init__.py` and `fixtures/run.py`, stamp the header as a release would, and run `release.sh --tag`. Once `--check-header` checks the manifest, that seed has none and every one of them would be refused, so `setUp` also runs the seed's `fixtures/run.py --stamp <version>` before its commit. A new test then edits `fixtures/run.py` in a later commit (pushed, so HEAD is still origin/main) and checks that `release.sh --tag` exits non-zero with `fixtures: run.py: its sha256 does not match MANIFEST — edited after its release` in its output, and creates no tag.
8. **The stamp step.** `release.sh <x.y>` runs the whole suite and the fixtures, which a throwaway seed cannot hold, so its stamp step is pinned by text. A test reads `release.sh`'s lines, leaving out comment lines (those whose first non-blank character is `#`), and matches whole lines, stripped of leading blanks, not substrings. It checks that a line is exactly `python3 fixtures/run.py --stamp "$v"`, coming before its first `python3 fixtures/run.py --check-header` after the branch is cut, that the line `(cd fixtures && git ls-files -z) | python3 fixtures/run.py --check-tracked` comes after the stamp and before the add (rule 2's tracked-files check), with lines `git checkout -q -- fixtures/MANIFEST` and `rm -f fixtures/MANIFEST` between it and the add, that a line `git add fixtures/MANIFEST` comes before its commit, and that its commit line names `fixtures/MANIFEST`. The tracked-files check, like the stamp, first runs for real at v2.4's release. The step itself first runs for real at v2.4's release, whose `--check-header` (in `release.sh`, before the commit) checks what it wrote.
