## The problem

An `event (<name>)` gate names one of v2.4's three typed checks, all of which read a forge or a file. Target design §4 sorts every wait into three kinds: what a typed check sees, what the host already witnesses (a precheck failing again, a person's press, a session's message), and judgment, which is work blocked on by id. The second kind has no check type. §4.2's *Later: `host-log`* sketches one, `host-log <kind> "<text>" [times N]`, with `since` "defaulting to the gate's `gate added` date".

Until it exists, such a wait is written as a retired `**Waits:** event — …` line, which no ledgerboard reader takes as a gate, or as `until <date>` plus a re-check entry, which is a guess on a date in place of the event. TD-046 cannot make a new `Waits` line an error until every wait has a gate form.

Three things the sketch leaves open have to be settled before it can be built:
1. **Where `times N` goes.** SPEC says the quoted text "runs from its opening `"` to the line's last `"` … and nothing follows it". The sketch puts `times N` after the text.
2. **What `since` is.** Ledger dates are days (*every ledger date is the UTC date*), and a host's records have times. And today only `new` writes a `gate added` line: a gate that `set` adds has none, so most gates have no date to count from.
3. **What the evidence is, and what the check may reach.** The other types reach a repo, and the host's visibility rule confines them. This one reads the host's own log, which holds mail and presses that may be private.

## Options weighed

**Where `times N` goes.**
- **(a) After the text, as sketched:** `host-log <kind> "<text>" [times N]`. The text would then run to the last `"`, and `times N` could follow it. That needs an exception to the one rule every type shares ("nothing follows it"), and a reader that sees `… "a" times 2` cannot tell the count from text unless it knows the type first. Rejected.
- **(b) Before the text (chosen):** `host-log <kind> [times <N>] "<text>"`. The quoted text stays the last argument, as in `file-contains`, so the shared rule stands unchanged and `parse_check()` reads the tokens before the quote as it already does.

**What `since` is.**
- **(a) Records on or after the day the gate was added.** This counts the same day's records from before the gate was written. The usual case is "the test fails again": the gate is written the day the test failed, so the failure that prompted it would pass the check at once. A false pass lifts the gate before the event, which is the failure TD-045 exists to prevent. Rejected.
- **(b) Records dated after the day the gate was added (chosen).** A record counts when its time is at or after 00:00 UTC of the next day. It never counts the event that prompted the gate. Its cost: an event later on the same day is missed, so the check waits for the next one, and the 30-day *Still waiting* item catches a wait that never recurs. A late pass costs a day, while an early pass costs the whole wait.
- **(c) A time on the `gate added` line.** Exact, but it gives one Log shape a time that no other line has, against the rule that every ledger date is a day. If (b)'s lost same-day event proves to matter in use, (c) is the later change. Rejected for now.

Whatever `since` is, it needs a `gate added` line, and **`set` writes none today**. Only `new` does, and only when it is given `filed` (`entry_text(filed=)`, module lines 3291–3303; `ledger.py new` builds it from `--by --session --words` together, refusing some but not all, `ledgerboard/ledger.py:1068-1075`). A `new` without `filed` writes no Log at all, so a gate filed that way stays undated and `check()` flags it (rule 4): a `host-log` gate is filed with `--by --session --words`, or added later by `set`. So this design makes `set` log `gate added: <gate>` for each gate it adds. That also fixes `gate_age()` for every gate `set` adds: today it falls back to the Log's first line, which can be months older.

**A gate with no `gate added` line** (hand-typed, or added before this release). Falling back as `gate_age()` does (the first Log line, then `Added`) would count records from before the wait began, which is a false pass again. So the check has no `since`. `check()` flags it (`event-undated`, below), and a host answers **error**.

**The evidence.** The other types cite where they were read (`<repo>#<n>`, `<repo>@<sha>`). This one cites the record that made the count reach N: its id in the host's log, a token of the Log's `[A-Za-z0-9_.@/-]+`, so a reviewer can look it up. shiftlead#TD-1295's records (`{at, kind, text}` in its Fix) need an id and the repo they concern. Both are named below as what that design must give.

**What it may reach.** A ledger is text anyone with PR rights can edit, and a lift PR is as public as the ledger. Without a bound, `host-log msg "<a guess>"` in a public ledger would test, one bit per sweep, whether any message the host ever logged contains the guess. Tying records to the ledger's repo limits which repo's events can be probed, but not how private their text is: a message about a public repo can still quote private mail. So the bound is the repo rule's, applied to the log and **denying by default**. A host counts only records it ties to the ledger's own repo, and answers a kind for a ledger only when it has declared that kind's records no more private than the ledger's repo (a precheck's failing test name, say). Every other kind is an error, and so is any case where it cannot tell.

## The rules

1. **The check:** `host-log <kind> [times <N>] "<text>"`.
   - `<kind>`: 1 to 40 of `[a-z0-9-]`, not starting with `-`. The kinds are the host's vocabulary (shiftlead#TD-1295's first are `precheck-fail`, `press` and `msg`). The package confines the token and never lists the kinds.
   - `times <N>`: optional, the word `times` then 1 to 3 digits with no leading zero (`[1-9][0-9]{0,2}`, so 1 to 999). Without it, N is 1.
   - `"<text>"`: as `file-contains`'s quoted text. It runs to the line's last `"`, nothing follows it, and it is not empty, not spaces alone and holds no control character. The host matches it literally and case-sensitively, as a substring of the record's text.
   - The arguments before the text are one token (the kind) or three (the kind, `times`, `N`). Any other count, a second token other than `times`, or an `N` outside its form is refused. `host-log times "x"` names the kind `times`.
   - **`parse_check()`'s record** for it is `{type: "host-log", kind, times, text, problem}`: `times` an int (1 when absent), and no `repo`. The quoted-text handling now inside `if kind == "file-contains"` (module 4585–4597) is lifted out to serve both types, and `host-log` gets its own argument branch before the `want` table and the repo and `@` handling, neither of which applies to it. Every reader of a check record that assumes `repo` (`lift_gate`, module 4354) branches on `host-log` first. The unknown-type message lists `CHECK_TYPES`' keys in order, so it becomes `unknown check type '<t>' — one of pr-merged, file-contains, ref-includes, host-log`, and the expected files that pin it are regenerated: `events/expected.json`, `grammar/expected.json` and `ledger/events.json`.
2. **Its outcomes.** `since` is `gate_added(text, "event (<name>)")`, the date of the entry's last `gate added` Log line for that gate in Log order, never the latest by date (rule 3; none: `None`). A record counts when it is of the kind, ties to the ledger's own repo, is dated at or after 00:00 UTC of the day after `since`, and its text contains the quoted text.
   - **passed:** the host's log holds at least N such records. The evidence is the id of the N-th, oldest first.
   - **not yet:** it holds fewer.
   - **impossible:** never, since a record may still come.
   - **error:** the host keeps an event log and cannot read it, does not know the kind or has not declared it answerable for this ledger (rule 7), or holds fewer than N records and its log no longer reaches back to 00:00 UTC of the day after `since`, the first instant counted (retention, so the count may be short); or `since` is `None`. Once N counted records are held, passed wins over retention.
   - **no outcome:** a host that keeps no event log gives none (`sweep()`: nothing). That way a host without the log, such as agent-cadence's runner, neither files *Event check broken* nor closes one another host filed.
   - **The cost of (b):** an event later on the day the gate was added is never counted, which is the common case for "the next Apply" written mid-day. The wait then runs to the next event, or to the 30-day *Still waiting* item. If that bites in use, the first change is a host-supplied instant or a time on the `gate added` line (option (c)).

   - **The count is the one host's**, from its own log, never summed across hosts. Hosts of one consumer that keep the log share it (shiftlead#TD-1295's log is the home's, one per install), so they agree. Two that keep different logs could disagree, one's `not yet` closing an *Event check broken* item another's `error` filed, and that item would be filed again on the next sweep. That flap is accepted as a known limit: the remedy is one log per consumer, not a rule here.
   - **A gate no host answers is silent.** With no outcome, `sweep()` neither lifts it nor files *Still waiting* or *Event check broken*, so the 30-day backstop does not reach it. A consumer writes a `host-log` gate only once a host that keeps the log sweeps its ledger (the Versions text says so).
   - **The evidence is trusted, not re-run.** A reviewer cannot re-run a `host-log` check from its evidence, as they can a forge check: the record id points into the host's own log. The lift rests on the host, as a person's answer rests on the person.

   Records are only ever appended and `since` is fixed while the gate and its check stand unchanged, so the count only grows: a passed check stays passed. A gate lifted and added again counts from its new `gate added` line, and from none if its re-adding wrote none (rule 3). **A changed question is a new wait:** a check whose kind, count or text is edited, or a gate dropped and re-added, would otherwise count from the old line and pass at once on records from before the new question was asked. So the writers date it anew (rule 5) and `check()` refuses an edit that does not (rule 4). A reopened entry whose gate survived keeps its `since`, records from its archived interval included, since the gate never lifted. `renumber` keeps the Log, so `since` too.
3. **`gate_added(text, gate) -> date | None`** (new): the date of the **last** `gate added` Log line, in the Log's order (the order the lines stand in, never their dates), whose gate is `gate`, compared as `gate_age()` compares (a person's name in any case). It has no fallback, unlike `gate_age()`. It is None, too, when a `gate lifted` line for that gate comes after that line in the Log's order, so a lift and a re-add on one day are told apart, and a hand edit that puts a later-dated line earlier changes nothing. So a lifted gate re-added by hand, with no new `gate added` line, never counts from the old one: it is undated, flagged and an error, where counting from the old date would pass it at once on the records since then.
4. **`check()`'s `event-undated`** (⚠, new): an open entry's `event (<name>)` gate whose Event section's check is `host-log` and for which `gate_added()` is None (no `gate added` line, or a `gate lifted` after the last). It is scoped as the other event flags: an error on an entry the edit changed, ℹ on a standing ledger. So it joins `EVENT_KINDS` (module 851), and through it `TEXT_KINDS`, and `event_problems()`'s and `check()`'s docstrings name it.
   - **On an edit** it also fires when the wait changed and was not dated anew. `check()` is given `old`; `event_problems(text, old_text=None, today=None)` gains the entry's old text and the day, `check()` passing `utc_day(today, …)` and, when `old` is not None, `old_texts.get(id, "")` at its call (module 822); with `old` None it passes no old text and this half does not run. It computes `_entry_texts(old)` before its per-entry loop (today it does so after, module 836). **The wait changed** when, against the entry's old text, the gate is newly carried or its `host-log` check changed: judged on `parse_check()`'s record (kind, times and text), so spacing alone is no change, or a check of another type became `host-log`, or the gate's `host-log` section is new (the old entry had none of that name).
   - **Dated anew** means all three of these hold. (a) The gate's `gate added` lines in the new Log, in Log order, compared as `(date, _gate_key(gate))` pairs over this gate's lines only, are its old ones as a prefix followed by at least one more, so the last, the one `gate_added()` reads, is an added line. Call its date L. (b) **floor ≤ L ≤ today**, where `today` is `check()`'s required `today` (module 801). The floor is the latest readable date in the old Log; with none, the first `YYYY-MM-DD` in the new entry's `Added` (as `gate_age()` reads it, module 3630); with none, there is no floor. A floor after `today` is lowered to `today`, so an honest line dated `today` is never refused for an old Log dated ahead. (c) When the old Log has a `gate added` line for the gate (the last in Log order, date P, even when a lift or drop made the old `gate_added()` None), L is `today` or after P. With none, (b) alone bounds it.
   - **What fails, and what passes.** A line inserted above the old last one fails (a). So does a pasted copy of an old line, wherever it is placed, since a copy keeps its old date (c). A backdated line fails (b), and so does a line dated after `today`. A writer's line is dated `today`, so an honest edit passes, a same-day one included. A PR checked on a later day than its line passes when L is after P. When it is not (the gate added on day D and its check edited on D, then checked on D+1), the check gives a false ⚠: the safe side, cured by an `edit` dated that day, and an accepted limit.
   - **Old text absent or unreadable.** An id absent from the old text (a new, reopened or renumbered entry, or `old=""`) has an empty old Log, so its floor is its `Added` date: its gate passes with a line dated from `Added` to `today`, and fails with none or one outside that. **An old text that raises** (below) fails closed: a changed wait on it is never dated anew, so it is flagged until the Log is repaired, since its old lines (and so a pasted copy of one) cannot be read. A new text that raises has `gate_added()` None and is flagged by the first clause.
   - **The accepted limits.** A hand-typed date between the floor (or P) and `today` is a deliberate misdating that review reads in the diff. A PR that renumbers or reopens an entry and also hand-edits its `host-log` check, keeping the old line, passes; renumber and reopen are tool writes whose PRs change nothing else. A standing ledger has no old text and cannot see a changed wait at all; the merge gate sees every edit. And a hand edit that backdates an existing `gate added` line, or removes one of several for the gate (removing its only one leaves `gate_added()` None, which the first clause flags), while the gate and its check stay unchanged is not a changed wait, so this half does not look at it: it is the same reviewed misdating limit.
   - **Unreadable Logs.** `log_lines()` raises `Refused` on an entry `canonical()` refuses (through `_entry_parts`, module 3143) and on a body with two Log sections (`_log_section`, 3561–3565); an unreadable line is an `unreadable` record, not a raise. `gate_added()` catches `Refused` from either and returns None, so the entry is flagged here and `check()` goes on, while `log-not-last` and `log-line` flag the Log itself.
5. **The writers date a new wait.** `edit` replacing an `**Event (<name>):**` section whose gate the entry carries, when its check changes to or within `host-log` (judged on the parsed record, as rule 4 judges it: a spacing-only change logs nothing), or when `edit` adds a `host-log` section the carried gate lacked, appends `- <today>: gate added: event (<name>)`, exactly as `set` appends its lines: the Log made at the end of the body if there is none, a Log that is not last refused, and the Status's notes not lifted. `edit` takes an optional `today` (B2 widens the tuple below to `_DATED_ACTIONS + ("set", "edit")`), refusing only that case without it; `plan_edit` passes its `day` to `edit` too (it passes none today, `ledgerboard/ledger.py:518`), and `fixtures/run.py` passes an `edit` step its case's own `today`, as for `set`. **`set` logs the gates it adds.** `edit_entry(text, "set", fields=…, today=…)` whose `Blocked by` adds a gate the entry did not carry appends `- <today>: gate added: <gate>` for each, in the canonical order the `Blocked by` is written in (`gate_items()`: decisions, `until`, events), creating the Log at the end of the body when the entry has none and refusing, as `note` does, a Log that is not last. Unlike `note`, it does not lift the Status's notes. A gate it keeps is not logged again. **The gates the entry carried** are its `gate_items()` plus, when its `Blocked by` holds the old form, that form's holder as `decision (<holder>)`, compared by `_gate_key` (a person's name in any case). So migrating the old form logs nothing, and `Decision (kim)` rewritten `decision (Kim)` is kept. Dropping a gate is unchanged: the lift and reassign routes write their own lines, and a gate dropped by `set` and re-added later by `set` gets a new line then, while one re-added by hand is refused by rule 4 on that edit. `set` now takes an optional `today` (SPEC's *Edits* refuses an argument an action does not take, so today `set` refuses it), and refuses a gate-adding `Blocked by` without it. A `set` that adds no gate is unchanged with no `today` or a valid one (an invalid one is refused by `utc_day`). The mechanism: `_DATED_ACTIONS` (module 3335, `note`, `archive`, `reopen`, which require `today` at 3828) is left alone. The stray-`today` check (3825) passes `set` too (a new tuple, `_TODAY_ACTIONS = _DATED_ACTIONS + ("set",)`). `set` validates `today` with `utc_day` only when it is given, and raises `Refused` when it adds a gate and `today` is None. `edit_entry`'s docstring ("taken by note, archive and reopen only", module ~3813) names `set` too, SPEC's *Edits* opening, where it says an argument an action does not take is refused, names `set` and `edit` as taking an optional `today`, and `fixtures/run.py` passes a `set` step its own `today` only when the case gives one (570–571's `dated` list passes `c.get("today", spec["today"])` to every step of the other three; `set` is not added to that list). `ledger.py`'s `plan_edit` passes its `day` to the `set` edit (it does not today, `ledgerboard/ledger.py:516`).
6. **The lift.** `lift_gate(…, evidence=)` for a `host-log` check takes a token of `[A-Za-z0-9_.@/-]+` (the record's id), and refuses anything else. There is no repo to compare. The Log line is the existing shape: `gate lifted: event (<name>) — by <host>; host-log passed; <id>`.
7. **Host rules** (SPEC's, not checkable by the package), denying by default: a host counts only records it ties to the ledger's own repo, and answers a kind for a ledger only when it has declared that kind's records no more private than the ledger's repo. Any other kind, or a case it cannot tell, is an error. The declaration is the host's own configuration, per kind, naming the most private class of repo the kind's records may be shown for; how it is written, and how the host learns the ledger repo's visibility, is shiftlead#TD-1295's to design. A host-log check reaches no forge, so the roster and visibility rule for repos does not apply to it; this rule takes its place.
