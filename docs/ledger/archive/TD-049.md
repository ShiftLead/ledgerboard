## TD-049: `check()` raises `Refused` on an entry with a field below its header block (a v2.4 regression)

**Priority:** High
**Type:** debt
**Added:** 2026-11-05
**Kind:** build
**Status:** Resolved 2026-11-04
**Taken by:** ao-ledgerboard-lb-techlead

**Why:** SPEC says a `Priority`, `Type`, `Blocked by` or `Part of` written below the header block "is still read, and flagged", and v2.3's `check()` gave an ℹ for it. v2.4's `check()` raises instead. TD-029 (#95) made it call `reassigns(text, gate)` for every `decision` gate, `reassigns()` reads `log_lines(text)`, and that reads `_entry_parts(text)`, which raises `Refused` for a field below the header block. `pickable()` still reads such an entry. So one entry in this shape stops `check()` for the whole ledger, and every caller of it gets a traceback: a consumer's `--check`, and agent-cadence's cadence-check `ledger` row. Repro: `check('# L\n\n## TD-036: x\n\n**Priority:** Low\n\n**Blocked by:** decision (Alex)\n', '', today='2026-11-04')`. agent-cadence found it while vendoring v2.4 (its TD-215). Its wrapper turns the `Refused` into one error naming the entry until a release flags it again.

**Location:** ledgerboard/__init__.py (`check()`'s gate loop, `reassigns()`, `log_lines()`, `_entry_parts()`), SPEC.md *Entries*, fixtures/ledger

**Resolved:** 2026-11-04 (PR #148) — fixtures/ledger/belowheader.md; SPEC.md Entries

**Done when:** The repro returns the ℹ for the below-header `Blocked by` line, with no exception, in a patch release.
