## TD-037: `board.py` and `ledger.py` give different exit codes, so exit 1 and exit 3 mean different things depending on which writer ran

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-04 (Paul, through his answer to m-26316e2c8d13 on PR #99; drafted by ao-ledgerboard-lb-techlead)
**Status:** Resolved 2026-11-03: board.py exits by ledger.py's table: 1 refused, 2 usage or an unusable ledger, 4 a write failed, never 3; SPEC and fixtures say so
**Taken by:** ao-ledgerboard-lb-techlead
**Blocked by:** TD-034
**Part of:** TD-010
**Location:** ledgerboard/board.py (main's exit codes, the module docstring's Exit line); SPEC.md The board writer (its Exit sentence) and Versions; fixtures (board writer cases that assert an exit code); tests

**Why:** v2.3's `board.py` exits 0 written, 1 a write failed, 2 usage, 3 refused. v2.4's `ledger.py` (TD-033, PR #99) exits 0 ok, 1 refused, 2 usage, 3 `needs`, 4 a write failed. Exit 3 cannot mean refused in `ledger.py` because target design §1.1 reserves it for `needs:`. So in one package a 1 or a 3 means different things depending on which writer ran, and every consumer wrapper has to map each writer on its own. That is the drift between writers that TD-033 exists to end. On 2026-11-04 Paul picked "merge as built + follow-up": #99's table is the package's, and `board.py` moves to it in v2.4, before any consumer wrapper relies on v2.3's codes.

**Resolved:** 2026-11-03 (PR #105) — SPEC.md The board writer (Exit) and Versions; ledgerboard/board.py

**Done when:** `board.py` and `ledger.py` share one exit table, SPEC says so in both writer sections and in Versions, the suite and fixtures pass, and this entry is archived before v2.4 is tagged.
