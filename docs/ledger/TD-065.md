## TD-065: Add a Doer: field to the board's act line, naming the repo or team that should do its step

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-11 (ao-shiftlead-designer-ao-1, through ao td add --repo; drafted by ao-ledgerboard-lb-techlead)
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** afae321f38024328aaae2f9637930f6a
**Location:** SPEC.md (The board; The board writer; Versions); ledgerboard/__init__.py (item_line, item_record, FIELDS_RE, FIELD_NAME_RE, ANY_FIELD_RE, WRITER_FIELD_RE); ledgerboard/board.py (add); fixtures/board/, fixtures/board_writer/, fixtures/edit/

**Why:** An `act` line on the board (a Do item) has no way to name who should do its step. ShiftLead's design TD-1543 (PR ShiftLead/shiftlead#3367, still in its revision rounds) adds **Have a session do it** to an `act` line: the person's press hands the step to a session. Paul's answer of 2026-11-11 to that design's steer (m-d713688a5506) chose to name the doer in a field, `Doer:`, not in the detail block's words, so the press can go straight to that repo's or team's techlead seat. The field is this repo's board format: ShiftLead and agent-cadence read the board only through vendored ledgerboard, so until `SPEC.md`, the module and `board.py` know `Doer:`, no consumer can write it or read it back. ShiftLead's TD-1661 waits on agent-cadence vendoring the release that has it (its Event *agent-cadence-doer*: `board.py` carrying `--doer`).

Asked for by ShiftLead's designer session (ao-shiftlead-designer-ao-1, mail m-0723fc81e7a5, about ShiftLead TD-1543). What it asked for: `Doer: <repo>.` (a registered repo's name) or `Doer: team <team>.` on an `act` line only, right after the line's `Context:` and ahead of its `Due:`, its value in the name grammar ledgerboard already uses for repo names; the writer refuses it on any other kind.

**Fix:** A design round first (Kind design-first): the shape is asked for, but this repo decides its grammar on its own long-term merit, not on one consumer's use. What the design settles:

- The field's grammar: the `<repo>` and `team <team>` forms, which existing name grammar each value reuses, and its place in an item line (after `Context:`, before `Due:`, as asked) against the field order `SPEC.md` *The board* gives.
- Whether it is a version event under `SPEC.md` *Versions* (a new field a v2 reader older than this release would read as text; whether it is part of the item key), and so which release carries it.
- What the reader and the writers do with it: `SPEC.md` *The board* and *The board writer*; `item_line(doer=)`; `item_record()`'s `doer`; `board.py add --doer`, refused on any kind but `act`; `Doer:` in the field-name sets (`FIELDS_RE`, `FIELD_NAME_RE`, `ANY_FIELD_RE`, `WRITER_FIELD_RE`) and in the list of fields that end `Context:`; and what a reply that contains `Doer:` does.
- Its fixtures: `fixtures/board/`, `fixtures/board_writer/`, `fixtures/edit/` as the design names.

Then the build(s) the design files, each landing its `SPEC.md` text with its code and fixtures; then a release (Paul's), then agent-cadence's vendor PR (its `board_edit.py add` passing `--doer` through), then ShiftLead's pin bump (its TD-1661).

**Done when:** A release of ledgerboard whose `SPEC.md` defines `Doer:` on an `act` line, whose module reads it into `item_record()`'s `doer` and writes it through `item_line(doer=)`, and whose `board.py add --doer` writes it on an `act` line and refuses it on any other kind, with fixtures for each; the precheck green.
