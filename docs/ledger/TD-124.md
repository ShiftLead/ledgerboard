## TD-124: An entry's sections are cut by a loose prose rule, so each new piece of data patches where a section ends

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-16
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** af871bd597f2458f8fc133ac1ba97e3f

**Why:** **Why:** An entry's body is cut into sections by a loose prose rule (SPEC.md, *The entry*): a section opens at any paragraph that starts with a bold run after a blank line, and runs to the next such paragraph. Data the tools act on lives in those prose sections (an Ask, an entry's own answers, which answers lift a hold), so where a section ends decides what the tools read. Three designs in a row have had to patch that edge. TD-109 accepted that an `**Ask:**` glued to the paragraph above it (no blank line) opens no section and is not read (its plan, D1). TD-111 refuses a bold run mid-text in a board item. TD-119 has spent three rounds on an `**Answers:**` or `**Lifts:**` glued to the section above, and on its answers' own bold runs; on 2026-11-15 the person held it with "Make Answers and Lifts each a single line, as your fallback says; the boundary rule has been patched three rounds running."

Every write, every aggregation (ShiftLead's home, its Queue and gate sweep, agent-cadence's attention report) and every merge-check verdict goes through this package, so structure must be exact and the same every time. People and sessions read the files themselves (PR diffs, a session reading an entry as its instructions, the person on GitHub, repairs when tools fail), so prose must stay readable. Today data and prose share one loose grammar, so each new piece of data needs its own patch to the boundary rule.

**Location:** SPEC.md (The entry: body sections); ledgerboard/ (the section reader)

**Fix:** **Fix (to design):** Review the body grammar so data is exact and prose is free inside exact edges. The starting point, from the person's conversation of 2026-11-15:

- **Section edges are strict.** A section opens only at a lead (a bold run ending in a colon) that starts a paragraph after a blank line. A lead-like line glued to the paragraph above it is flagged by the check, not silently read as prose; a bold run elsewhere in prose stays prose.
- **Data sits in one-line fields.** A value the tools act on (an Ask, an entry's answers, its lifts) is one line, `**Name:** value`, never a multi-paragraph section. This is TD-119's fallback, made the general rule.
- **Nested data goes in a fenced JSON block,** only where one line cannot hold it, so it parses exactly and still diffs readably. One-line fields stay the first choice; JSON is the exception.
- **Prose sections (Why, Fix, Context, Done when) stay free text.** The tools only find where they start and end.
- **A migration plan:** what the check flags in each repo's ledger and board today, how existing entries are rewritten (by the writer, in a release of its own, as v2.7's and v2.8's migrations were), and the order across ledgerboard, agent-cadence and ShiftLead.

Decide each rule on long-term merit, not on a consumer's current usage or the cost of migrating. This design owns the section-edge rule: TD-119 builds its Answers and Lifts as single lines to it rather than patching the edge again.

**Done when:** **Done when:** A design PR states the body grammar (section edges, one-line data fields, where JSON is allowed, what the check flags) and its migration plan; review rounds converge; the person says Go; and the builds are filed, held until then.
