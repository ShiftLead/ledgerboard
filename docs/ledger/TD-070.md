## TD-070: Evaluate and design the board as a directory, one file per item with a stable id, for v3.0

**Type:** debt

**Blocked by:** decision (paul)

**Why:** The board is one file, and `board.py add` writes every new item at the same place: above the first item of its section (`_under()`, `plan_add()`). Two PRs that each add an item therefore always conflict, and GitHub's merge runs no merge driver, so each collision is a rebase and a full precheck again. No layout inside one file avoids it: two inserts at one anchor conflict wherever the anchor is. agent-cadence's TD-248 (2026-11-07) gave the rebase a tool, `board_edit.py replay`, which removes the hand edit but not the rebase or the precheck, and its closing note left the layout to this repo.

The v2 ledger split (*The ledger as a directory*) ended the same problem for entries. Measured on 2026-11-11 from the git output in one machine's session transcripts since 2026-10-12: about 140 conflict events on v1 ledger files, 3 on v2 ledger directories, and 7 on boards (a floor: ShiftLead's TD-1482 counted more than six board rebases in one burst of design PRs, one PR rebased three times). So the board's conflicts are real and far rarer than the ledger's were; they alone do not justify a major.

The case for the directory is the item's shape. A `decide` item is now a line of one to two kilobytes with a detail block and a life of its own (open, decided, closed, archived), which is an entry's shape. Its identity is the item key, the line with some fields cut out, which consumers persist and which no release may change within a major. One file per item, named by a stable id, would replace the key with the id, turn the archive into a file move (`archive_closed()`, its refusals and `ARCHIVE_AT` go), and end both the open-and-closed-twin rule and `replay`. Collisions also grow with the number of PRs open at once, which is rising.

It is a major: a v2 reader cannot read a directory. Paul asked for the evaluation on 2026-11-11 and asked for this entry.
