**Why:** `Parts:` has been read, ordered and keyed since v2.3, and SPEC says "what an answer does to the parts it lists is v2.4's, and so is its writer". The target design's v2.3 row says the same: "the writer that fills it and checks the parts' gates comes in v2.4". v2.4 shipped `covers()`, `decide_lift()` and `closes()`, which all read `Parts:`. It shipped no writer: `item_line()` takes no `parts=`, and `board.py add` has no `parts` in `TAKES["add"]`. A design's end-of-rounds item is meant to hold all its builds at once: one `decide` whose Context names the parent and its gate, with the builds in `Parts:`, which `covers()` counts as covering each build's gate. Without a writer, a consumer's sweep files one `Go | Not yet` item per held build beside it. The consumers then have no `Parts:` to show either: agent-cadence's `board_edit.py` passes `add` through, and ShiftLead's Queue (its TD-1378) shows the board. Asked for by agent-cadence TD-221.

**Ask:** Go to file TD-050's two builds (B1: `item_line(parts=)` and `parts_problems()`; B2: `board.py add --parts`), or buy one more review round for round 9's fixes (F105-F109: an id in `archived` with no text reads as archived, and four fixture and order clarifications).

**Related:** agent-cadence TD-221, ShiftLead TD-1378, TD-051, target design §6 (*Parts*), SPEC *The decide lift* and *Closing on the answer*

**Done when:** Both builds merged: `board.py add --parts` writes the field in number order and refuses it on a non-`decide`, a bad id or Context, no lifting answer, and a snapshot `parts_problems()` faults; the plan's fixtures pass, `covers()` reading each listed part as covered by the parent's item among them; and SPEC's text from the plan landed with the code.
