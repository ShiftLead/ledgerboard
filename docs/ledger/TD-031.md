## TD-031: A gate that nobody is asked about waits silently, and each consumer would decide on its own what to file and when

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-03
**Status:** Open
**Taken by:** 2e9dce7d0dea
**Blocked by:** TD-030
**Part of:** TD-010
**Location:** ledgerboard/__init__.py (covers, sweep); SPEC.md The gate sweep; fixtures/sweep

**Why:** Without a sweep, a decision with no board item, a broken event check or a month-old wait sits unseen. The rules are format logic both consumers need, so they belong in the module; the consumer keeps the I/O (target design §1.2, §3.2).

**Fix:** Per target design §1.2 (*The sweep's functions*) and §3.2:
- `covers(entry_text, gate, boards, repo) -> [(board, item, state)]` with states `open`, `decided`, `closed`, `closed-decided`, reading each board's archive through `parse_closed_items`, parent snapshots included, on a board whose `People:` lists the gate's person;
- `sweep(entries, boards, results, today_utc, today_local, reask_days, event_age_days, repo) -> {to_file, to_close, lifts}`: §3.2's table; the person's board pick by `origin_key`; one filing rule keyed on (Context key, kind, condition); the re-ask window counting only non-lifting answers; the close rule with its backstop; `lifts` for reached `until`s and passed events;
- the sweep's item heads and answers (`Keep waiting`, `Not yet`, `Lifts: Drop the gate.`).

**Done when:** Both functions are built with SPEC text and fixtures (entries, boards and results in; items to file and close and lifts out, including each fixture §1.2 and §3.2 name), and the suite passes.
