## TD-030: Which id comes next, and whether a new entry's id was really given to it, is judged in a consumer script the format doesn't define

**Priority:** Medium
**Type:** feature
**Added:** 2026-11-03
**Status:** Open
**Taken by:** 2e9dce7d0dea
**Blocked by:** TD-029
**Part of:** TD-010
**Location:** ledgerboard/__init__.py (ids_held, next_id, parse_take, judge_takes); SPEC.md The next id; fixtures

**Why:** The id counter and the merge gate's judgement of `Id take` live only in agent-cadence's `ledger_next_id.py`; the format doesn't define the counter, so another consumer would write its own (target design §1.2; agent-cadence TD-188).

**Fix:** Per target design §1.2 (*The next id*):
- SPEC defines the counter: the branch `cadence/ledger-ids`, its one file `LAST`, and a take as one fast-forward commit whose body carries `by`, `branch` and `take`;
- `ids_held(files) -> set[int]` (headings, entry file names, table rows, outside HTML comments; refuses a newer major);
- `next_id(last, ids, floor) -> (int, warnings)`;
- `parse_take(subject, body)` (an id or a range, and its body fields);
- `judge_takes(new_ids, takes, entries, branch, default, accept_taken_by=False) -> (fails, warns)` with today's kinds, every take kept so a doubly given id is judged against all of them and a failure names the other id's take.

**Done when:** The four functions and the counter's SPEC text are built with fixtures (taken from agent-cadence's `ledger_next_id.py` tests' cases, rewritten as invented data), and the suite passes.
