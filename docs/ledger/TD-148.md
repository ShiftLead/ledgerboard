## TD-148: A v1 entry ending in its Ask is flagged when an entry separator follows it

**Priority:** Medium
**Type:** debt
**Added:** 2026-11-18 (agent-cadence's grinder, through an entry request; drafted by ao-ledgerboard-lb-techlead)
**Owner:** designer
**Kind:** design-first
**Status:** Open
**Id take:** 2f6c6f691ac24e818f4b9160467ee24d
**Blocked by:** decision (paul)
**Part of:** TD-124

**Why:** v3.3's `field-lines` check flags an entry in a v1 ledger whose last section is its `**Ask:**` line, because the `---` line that separates it from the next entry is read as text past the Ask's line. v1 ledgers in use put a `---` line between entries (agent-cadence TD-283 reports it; its seed, `files/docs/technical_debt.md`, shows a `---` rule only around its Summary table), so every such ledger whose entry ends in an Ask gets the flag. Migrating cannot cure it: `migrate-body` would move the `---` under a `**Context:**` lead, and the writer refuses edits to the flagged entry. Reproduced on main: `_body_faults("**Why:** x.\n\n**Ask:** Should it? Yes or no.\n\n---\n\n")` returns `[('field-lines', 'ask', 'lines', 2)]`; with the `---` before the Ask instead, nothing is flagged. Found by agent-cadence's grinder while vendoring v3.3 (agent-cadence TD-283). TD-124's design (D3, D6) does not mention a thematic break.

**Design PR:** #440

**Ask:** Should the design that stops a separator line after an entry's question being read as part of it get one more review round?

**Location:** ledgerboard/__init__.py (_body_faults, _ask_reading, migrate_body); SPEC.md (The body's shape, data fields)

**Fix:** Designed: [docs/plans/TD-148-closing-rule.md](../plans/TD-148-closing-rule.md) (rounds: [docs/reviews/TD-148.md](../reviews/TD-148.md); in plain words: [docs/synopses/TD-148.md](../synopses/TD-148.md)). A thematic break that is the body's last line with words, read with comments dropped, below a blank line or with no line above it, is the entry's closing rule; it and the lines around it with no words are the entry's closing tail, held by no section, in every version (D1). Readers read the body without it; writers keep it as the entry's end, one blank line put above it only where the tail does not open blank once dropped; `_entry_parts()` cuts it, `_entry_tail()` and `_render(tail=)` carry it. `migrate-body` leaves it (D2); `split()` is unchanged (D3). One build on Paul's go, B1: the plan's SPEC text, the code and the fixtures in one PR, then a minor release (v3.5 or the next free minor). No consumer changes code; each takes the release in its routine vendor PR.
