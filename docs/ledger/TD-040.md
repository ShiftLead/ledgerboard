## TD-040: Fixtures do not name the release they apply to, so a consumer cannot run the set for its own pin

**Why:** Target design §7.4's last bullet: "Fixtures carry the release they apply to, so a consumer can run the set for its own pin (CommonMark publishes its tests per spec version)." Nothing spells how: SPEC, the design and `fixtures/run.py` name no field, file or option for it. TD-035 carried it as one bullet of its Fix. On 2026-11-04 Paul answered the steer that asked for its shape (m-8dbfc6bf991c; his reply m-537d6a2b218f) by splitting it off, so it is designed here before anything is built.

**Ask:** Say Go to file TD-040's one build (the fixture set names its release in `fixtures/MANIFEST`, in v2.4), One more round for another review, or Hold with a note.

**Fix:** [the plan](../plans/TD-040-fixture-release.md), option (c). The set, not each case, names its release: `fixtures/MANIFEST`, a release line (`# ledgerboard v<x.y> fixtures`) and `<sha256>  <path>` for every other file in the set, sorted by path bytes. `run.py --stamp <x.y>` writes it and `run.py --check-tracked` compares it with what git tracks (fed on stdin; `run.py` runs no git); `release.sh` runs both when it stamps the headers and commits the manifest with the package. `run.py --check-header` checks it beside the headers: intact, nothing added or missing, and the package's release. A plain run reads no manifest, so the precheck is unchanged between releases; a new test stamps the real set in every precheck so a refused or untracked fixture fails its own PR. The existing `--check-header` tests and the ReleaseTag seed run a stamped copy. One build, in v2.4, so TD-036's tag waits on it. It is filed on Paul's go, and its Fix carries F47–F51 and R17's two remarks, which no design review has read (*fixed, not reviewed; the builder checks it*). A consumer vendors the set whole, with `-text` on its path; its vendor check (`--check-header`) then proves the set and the package are one release.
